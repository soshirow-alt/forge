# Forge UI copy rules（恒常）

Cursor / 実装者が **毎回** 参照する UI 文言・情報設計ルール。  
要約は `.cursor/rules/forge.mdc` と `AGENTS.md` にも載せる。詳細・例外は本ファイル。

原典の概念層（学習ループ整理用の「初声」「声を届ける」）は残してよい。  
**ユーザー向け画面に「声」を出さない**ことが本ルールの中心。

---

## A. Forge UI 用語

### 禁止（ユーザー向け UI）

次をボタン・タブ・見出し・空状態・バッジ・説明文・OG 文言・デモ画面のユーザー向け文字列に使わない。

- 「声」
- 「声を届ける」
- 「みんなの声」
- 「プレイヤーの声」
- 「届けた声」
- 「届いた声」
- 「初声」（プレイヤー向け表示。内部・原典・法務定義は例外可）

### 使う語

| 用途 | 表記 |
|---|---|
| 原則 | **フィードバック** |
| 短いバッジ内のみ | **FB**（例: `採用FB 3件` / `初期FB`） |
| タブ例 | みんなのフィードバック |
| CTA 例 | フィードバックする |

### バージョン表記（ユーザー向け UI）

ユーザー向け UI では、一般的な version 表記としての「版」を原則使わない。

| 用途 | 表記 |
|---|---|
| 短い表示・バッジ | **ver**（例: `ver 0.1` / `最新ver` / `次ver`） |
| 文章 | **バージョン** |

禁止寄り:

- 最新版 / 次版 / この版 / N版 / 版ごとの声

推奨:

- 最新ver / 次ver / このver / ver N / verごとのフィードバック

**例外（許容）**:

- 状態ラベル・プロダクト用語としての **正式版**
- 開発フェーズ文脈の **正式版候補**
- 例: Special Thanks バッジ「正式版まで見届け」
- これらを **「正式ver」に置き換えない**（不自然なため）

DB・内部名・過去 docs の `version_*` や「版」は即リネーム不要。表示文字列だけ寄せる。

### リネームしないもの

- DB / RPC / テーブル / カラム / コード識別子の `voice_*`（例: `voice_adoptions`, tab id `voices`）
- DB / 内部の `version_*` 等
- historical docs・旧設計メモの過去表現
- 「音声」「声優」など別意味の「声」

これらは **即リネームしない**。ユーザー向け表示文字列だけ直す。

## B. 文字量・情報設計

1. 長い説明文を置く前に、**バッジ・チップ・アイコン・表・カード構造**で表現できないか検討する
2. セクション説明文は **原則置かない**。置く場合も **1 行まで**
3. プレイヤー一覧・貢献一覧は文章ではなく **カード / 表 / バッジ** で整理する
4. 「なぜ載っているか」は短いラベルで示す（例: `見届け中` / `初期FB` / `採用FB 3件`）
5. 日付・ver・件数は本文に混ぜず、**右側メタ / バッジ / チップ**
6. 同じ意味の情報を左右・上下に **重複表示しない**
7. 「この画面の目的」「誰に何を伝えるか」を決めてから項目を置く
8. 説明が必要な UI は、まず **UI 構造が悪い** と疑う

NG 例:

- 「この作品の更新や改善に関わったプレイヤーです。」を増やす
- 「〜したプレイヤーです」で説明する
- 小さい文字で補足を何行も積む
- 右に ver、下に同義の文章を重ねる
- 「最新版」「次版」「N版」など、一般の version を「版」で書くこと（**正式版** / **正式版候補**は例外）

## C. Special Thanks

| 項目 | 内容 |
|---|---|
| 場所 | `/games/[id]` の作品詳細タブのみ |
| ではない | Forge 全体の `/special-thanks`、LP 下部、footer 導線、プラットフォーム名簿 |
| 目的 | **この作品に誰がどう関わったか** を見せる |
| 体験目標 | フィードバックしたくなる / 見届けたくなる / 名前が載ることが嬉しい |
| ではない | 開発ログ風・分析風・説明文の羅列・FB 本文一覧 |

セクション（開発中 / 正式版後）は維持してよい。  
同じプレイヤーが複数セクションに出てもよい（関わりが複数あるため）。  
ただし各セクションで **載っている理由をバッジ / メタで明確にする**。文章で補わない。

---

## D. UI 確認ルール（一覧・カード）

一覧・カード・ランキング風 UI は、**1 件だけの seed で PASS にしない**。

最低限確認する:

- 10 件以上
- 長い display_name
- avatar あり / なし
- handle あり / なし
- 複数 ver・複数件数
- desktop 2 列（または横幅を使うコンパクト表）
- 「ほか N 人を見る」等の展開
- mobile 1 列での崩れ
