## 1. ロードマップ分類

### MVP として最低限必要なもの

| 領域 | 状態 |
|---|---|
| 発見（一覧・検索・詳細閲覧） | **実装済み** |
| ログイン必須のプレイ・外部リンク | **実装済み** |
| 構造化 FB（プレイ後） | **実装済み** |
| 作品投稿・編集 | **実装済み** |
| 応援 / 追跡 / 保存 | **Supabase 化済み** |
| 開発ログ + 開発の歩み表示 | **実装済み** |

| devlog → watch 通知 | **実装済み** |
| 開発フェーズ 4 名称 | **実装済み** |

### まだ未実装の重要機能

| 機能 | 重要度 | 備考 |
|---|---|---|
| **新版公開 → プレイヤーへの再プレイ促し** | 高 | 004 で技術基盤はあるが、ループが「再プレイ」で途切れる |
| game extras（focus_notes / プレイ時間）の DB 化 | 中〜高 | 別端末で開発者情報が消える |
| テスター応募数の DB 化 | 中 | LS 依存 |
| 通知の完全 Supabase 化（FB 等） | 中 | devlog 通知のみ DB、他は LS 混在 |
| プレイヤー向け「現行版 / 新 FB 枠」の機能的表示 | 中 | copy だけでなく状態表示 |
| 旧版 FB のプレイヤー向け履歴 | 低〜中 | 004 で意図的に後回し |

### 実装済みだが弱い機能

| 機能 | 弱さ |
|---|---|
| コアループ「再プレイ」 | 新版公開後、watch ユーザーが気づけない |
| ホーム discovery タブ | 「テストプレイ受付中」の意味が弱い（オーナー確認済み） |
| プレイヤー向け改善材料 | 全版 FB 混在・版ラベルなし |
| 通知体験 | LS 混在、Realtime なし、版 bump 未通知 |
| 本番コンテンツ | mock 中心、実作品 1 件 |
| テスター募集フロー | 応募数 LS、Forge 原典上は手段の一つに過ぎない |
| returnUrl | プレイ導線のみ（他アクションは `/` 固定） |

### 後回しでよい機能

- P1 UX copy（ホームタブ説明、版表記統一など）
- 作品単位 dashboard 新規 page
- AI FB 要約 / 開発者返信
- アナリティクス / Forge SDK 実装
- ランキング・バッジ・課金
- phase CHECK 制約・status 一括整理
- ホームタブ統合（新着 / 人気 / 最近更新）
- Realtime 通知

## 2. 現在地

### 完成していること

- **技術的コアループ**: 投稿 → 発見 → プレイ → FB → devlog（版 bump 可）→ 同版編集 / 新版 FB 枠
- **データ基盤**: Supabase migrations 001〜004、9+ テーブル
- **開発者導線**: P0 で「次にやること」が見える
- **原典整合**: ログイン方針、応援 1 回、構造化 FB、送客ではなく Forge 上に反応が残る設計

### 未完成のこと

- **体験としての成長ループ**: v0.1→FB→v0.2→**再プレイ→新 FB** がプレイヤーに伝わらない
- **本番の実データ**: 実作品が少なく、mock が discovery を占める
- **localStorage 残**: extras、応募数、フォロー、一部通知
- **E2E 実地確認**: 004 版別 FB の本番 E2E はオーナー手順ベース

### リリース前に必須

| 項目 | 理由 |
|---|---|
| 実作品 1 本以上での **コアループ E2E** | 投稿〜FB〜devlog〜版 bump が本番で通ること |
| **再プレイ接続**（通知 or 同等の機能的導線） | Forge 原典ループの最後の 1 節が空 |
| **extras DB 化**（最低 focus_notes） | 開発者が別端末で作品情報を失うリスク |

※ P1 copy 改善、ホームタブ再設計、作品 dashboard 新設は **必須ではない**（オーナー判断済み）

### リリース後でもよい

- ホームタブ統合
- 旧版 FB プレイヤー表示
- アナリティクス
- AI / 開発者返信
- クリエイターフォロー DB 化
- returnUrl 拡張

## 3. 次に着手すべき 1 テーマ（Cursor 推奨 1 位）

### テーマ名

**「新版公開 → 再プレイ → 新 FB」ループの接続**

（版 bump 時に watch ユーザーへ通知し、作品詳細で「新しいプレイ可能版」を機能的に示す）

### なぜ 1 位か

1. **Forge 原典のコアループの最後が未接続**  
   004 と P0 で「投稿〜FB〜改善（devlog）」までは成立。プレイヤーが **再プレイして新 FB を書く** 瞬間だけ、システムが黙っている。

2. **P1 copy 改善と違い、機能ギャップの解消**  
   ラベルや説明文の polish ではなく、「知らないと次のアクションが起きない」問題。オーナーが P1 を保留した今、**体験の穴を 1 つ塞ぐ** フェーズに合う。

3. **既存資産の上に載せられる**  
   - `project_watches` 済み  
   - `user_notifications` + devlog 通知パターン済み  
   - `addDevlog` + `publishPlayableVersion` 済み  
   → 新 page 不要。通知 1 種 + 詳細の最小状態表示で着手可能。

4. **開発者・プレイヤー双方にリターン**  
   - 開発者：devlog で版を上げた結果、プレイヤーが戻って FB が増える  
   - プレイヤー：watch した作品の「成長」を体感できる（Forge の差別化）

5. **localStorage 解消より先**  
   extras DB 化は重要だが **開発者の運用改善**。本テーマは **Forge コンセプトそのもの**（成長を見届ける）に直結。

## 4. 実装したときの効果

### プレイヤー体験

- 追跡中の作品が **新版公開** されたら通知で気づける
- 「また遊べる / 新しい FB を書ける」が明確になる
- 単発プレイヤー → **ループに戻るリピーター** になりやすい

### 開発者体験

- devlog + 版 bump の **効果が FB として返ってくる** 実感
- 「改善を書いても誰も来ない」感が減る
- 開発ダッシュボードの FB が **版ごとに増える** 流れが自然になる

### Forge コンセプト

- 「完成前ゲームの **成長**」が **プレイヤーにも見える・参加できる** 形になる
- Steam 前段階として「同じ作品が育っていく」体験の核
- 送客サイトではなく **Forge 上でループが回る** ことの証明
