# 設計レビュー — プレイヤー「俺がこのゲームを育てた」コア体験

**ステータス**: 設計レビュー（**未 GO・実装なし**）  
**日付**: 2026-06-16  
**位置づけ**: Forge 競争優位の本体。P0/P1 完了後の最優先設計テーマ

**原典**: `docs/forge-principles.md` — プレイヤーサイクル「声を届ける → **変化を見る** → 再プレイ」  
**関連**: `docs/player-voice-adoption-ai-design-review.md`（AI 紐づけの技術案。本書は**体験全体**の評価）

---

## 0. 結論（先に）

**「更新された」だけでは Forge のコア価値は成立しない。**  
**「俺が変えた」と感じるには、プレイヤー個人の因果ストーリーが必要。**

| 論点 | 結論 |
|------|------|
| コア体験として成立するか | **通知単体では NO**。A + 永続レジャー + 再プレイ接点 の**三層**なら YES |
| 最も「俺が育てた」感 | **案A（個人マッチ）** が最強。B/C 単独では弱い |
| 開発者負担ゼロ | **A/B/C すべて自動化可能**。ただし devlog 品質が低いと偽陰性増 |
| 5年耐え | **データモデル（voice↔update リンク）を正本**にし、AI は交換可能なマッチャーに留める |
| Forge らしさ | 個人の物語・版固定・具体引用。**ランキング・採用率・バッジは Out** |

**Cursor 推奨（正式機能）**:  
**案A を核** + **案D-1 個人インパクトレジャー** + **案D-2 再プレイ時接点**。案B は A の補助。案C は作品公開面の「声が届いている」証拠（匿名テーマ）。

---

## Q1. プレイヤーはどの瞬間に「俺が育てた」と感じるか

### 心理構造（Steam にないもの）

「育てた」は **感情ラベル** ではなく **因果の自己帰属** である。

プレイヤーが内側で成立させている式:

```
俺が v0.3 で「X」と言った
  → 開発者が（Forge 上で）ゲームを更新した
  → v0.4 で X に関係する変化が実際にある
  → 俺が再プレイして確認できた
```

**4つの必要条件**:

1. **具体性** — 「X」が自分の言葉として思い出せる（抽象「反映された」は不可）
2. **時間連続** — 前回プレイ → 回答 → 待つ → 変化、の弧がある
3. **個人帰属** — 「23人も言ってた」より「俺が言った」（B だけでは弱い）
4. **検証可能性** — 再プレイで「本当に変わった」を自分の目で確認

### 「育てた」と感じる瞬間（優先順）

| 順 | 瞬間 | なぜ効くか |
|----|------|-----------|
| 1 | **再プレイ中** — 以前言った点がゲーム内で変わっているのを体感 | 最強。身体感覚で帰属が確定 |
| 2 | **変化通知を開いた瞬間** — 自分の引用 + 更新内容の対が並ぶ | A の理想形 |
| 3 | **マイページで「自分の声の年表」を見返す** | 単発通知より長期の関係性 |
| 4 | **待っている間** — 「あなたの声は v0.3 に届いています。次の更新を待っています」 | 参加感の維持（未実装） |

### 現在の Forge で起きていないこと

- 瞬間 1: 新版バナーは「更新あり」止まり。**自分の声との接続なし**
- 瞬間 2: 通知は devlog/新版。**voice↔update の因果 UI なし**
- 瞬間 3: **プレイヤー向け「自分の回答履歴」画面が存在しない**
- 瞬間 4: 回答送信後は「届きました ✓」で**サイクルが途切れる**

## Q2. 開発者負担ゼロ（または極小）で実現できるか

### 結論: **YES — ただし前提がある**

| 前提 | 内容 |
|------|------|
| 自動マッチのみ | 手動「採用しました」UI は禁止（オーナー判断） |
| devlog が更新の公式記録 | ゲーム外だけ直して devlog なし → **プレイヤー側は検知不可**（許容する取りこぼし） |
| 低 confidence は通知しない | 開発者の確認作業に**転嫁しない** |
| 品質は AI + 集計で担保 | 開発者は今どおり「記録して公開」だけ（Studio P0 済み） |

### 開発者負担が増える NG パターン

- 回答ごとに採用チェック
- devlog 作成時に「参考にした声」を選ぶ
- 誤判定のたびに開発者が DM 対応

### 極小負担で許容されること

- devlog タイトルをプレイヤー向けに書く習慣（**強制しない**。AI が要約補完）
- 公開フローは現状維持（記録 → 新版公開）

## Q3. Forge らしい形は何か

### Forge らしい

- **版（version）に縛った物語** — 「いつ・どの版で・何を言い・何が変わったか」
- **1対1の引用** — ランキングではなく個人のセリフと更新の対
- **再プレイで閉じる** — 見るだけで終わらせない
- **匿名の集計は補助** — 「みんなの声」グラフは**参加の入口**、帰属の出口ではない
- **断定より具体** — 「反映されました」< 「あなたは "…" と言い、今回 "…" された」

### Forge らしくない（原典・out-of-scope）

- 採用率・貢献度スコア・バッジ・リーダーボード
- 「トップ貢献者」表示
- Steam 的レビュー競争
- Discord 的リアルタイム会話の代替

### ブランドメッセージとの整合

> **まだ誰も知らないゲームを、一緒に面白くする。**

「一緒に」の本体 = **俺の声が形になった** という実感。更新通知だけでは「一緒に」にならない。

## 案 A / B / C / D の評価

### 評価軸

| 軸 | 意味 |
|----|------|
| **育てた感** | 「俺が変えた」の強度 |
| **運用負荷** | 開発者 + 運営 |
| **5年** | スケール・信頼・モデル交換 |
| **誤判定耐性** | 間違い時のダメージ |

### 案A — 個人 AI マッチ（回答 ↔ 更新）

```
あなたは「チュートリアルが欲しい」と回答しました
↓
今回、チュートリアルが追加されました
```

| 軸 | 評価 |
|----|------|
| 育てた感 | **★★★★★** 最強。個人帰属が直球 |
| 運用負荷 | **★★★★★** 自動。devlog 公開トリガー |
| 5年 | **★★★★☆** voice_adoptions 正本 + AI 交換可能 |
| 誤判定 | **★★★☆☆** 偽陽性が信頼を壊す。閾値・無通知設計必須 |

**判定**: コアの**核**として採用すべき。ただし**通知だけでは不十分**（後述 D 必須）。

---

### 案B — 同意見グループ通知

```
あなたを含む23人が「チュートリアル不足」と回答しました
↓
今回、チュートリアルが追加されました
```

| 軸 | 評価 |
|----|------|
| 育てた感 | **★★☆☆☆** 「俺が」より「俺たちが」。個人帰属が薄れる |
| 運用負荷 | **★★★★★** クラスタリング自動化 |
| 5年 | **★★★★☆** クラスタ ID を DB に持てば可 |
| 誤判定 | **★★★★☆** 個人への誤通知は減るが、**無関係な人への通知**リスク |

**判定**: **A のフォールバック**（個人 confidence 不足だがクラスタ一致時）。単独コアにはしない。

---

### 案C — 更新ごと「今回反映された声」を公開

```
今回反映された声
・説明不足
・チュートリアル不足
・難易度が高い
```

| 軸 | 評価 |
|----|------|
| 育てた感 | **★☆☆☆☆** 集合の証拠。**「俺」が特定できない** |
| 運用負荷 | **★★★★★** devlog 公開時に AI テーマ抽出 |
| 5年 | **★★★★★** 匿名テーマは安定 |
| 誤判定 | **★★★★☆** 個人誤通知はない。テーマのズレは許容 |

**判定**: **作品詳細の公開面**（「このゲームは声を聞いている」）として有効。**コア体験の出口ではない**。Steam にない「声が届く文化」の背景として有用。

---

### 案D — 追加案（Cursor 推奨）

#### D-1. 個人インパクトレジャー（「自分の声の年表」）

- マイページ / 作品詳細に **ログイン本人のみ** のタイムライン
- 各項目: 版 · 自分の回答引用 · 状態（届いた / 更新待ち / **つながった** / 再プレイ済み）
- 通知が来なくても **関係が可視化** される（長期の「育ててる」）

| 育てた感 | **★★★★☆** 通知より持続。複数サイクルで「このゲームを育ててきた」 |
| 運用負荷 | **★★★★★** A の結果を表示するだけ |

#### D-2. 再プレイ接点（新版プレイ開始時）

- 新版初回プレイ前/直後: 「前回 v0.3 であなたは "…" と答えました。v0.4 で変わった点を確認してみてください」
- **もう一度プレイする** CTA と一体（P1 済み導線の延長）

| 育てた感 | **★★★★★** Q1 瞬間1 に直結 |
| 運用負荷 | **★★★★★** A のメタデータを流用 |

#### D-3. プレイヤー側 nurture 状態（待ちの可視化）

- 声を届けた → **育成中** → 変化が届いた → 再プレイ待ち
- 開発者 Studio のフェーズの**鏡像**（イベント語ではなく工程語）

| 育てた感 | **★★★☆☆** 単独では弱い。**A/D-1 と組み合わせで強い** |

#### D-4. devlog 構造の軽い規約（非強制）

- 公開 devlog に AI が **プレイヤー向け一行要約** を自動生成（開発者編集可だが**必須ではない**）
- マッチング精度向上 + P1 更新 UI の見出し品質向上

---

### 案の組み合わせ（推奨）

```
【コア体験 = 三層】

Layer 1  個人因果（案A）     … 「俺の言葉 → この更新」
Layer 2  永続関係（案D-1）   … 「このゲームを俺は育てている」年表
Layer 3  身体確認（案D-2）   … 再プレイで「変わった」を体感

【補助】
案B … A の confidence 不足時
案C … 作品詳細の匿名「届いた声のテーマ」（発見・信頼の土台）
```

## 7項目への直接回答

### 1. どの案が最も「俺が育てた」感を出せるか

**案A（個人マッチ）+ 案D-2（再プレイ接点）の組み合わせ。**

通知文だけの A は「嬉しいが浅い」。**再プレイで確認した瞬間**が最強の帰属。D-1 がそれをサイクル全体で記憶させる。

### 2. どの案が開発者負担ゼロで運用できるか

**A / B / C / D すべて開発者追加作業ゼロで設計可能**（公開フロー現状維持）。

ただし **devlog を書かない開発者** はプレイヤー側で取りこぼしが出る — これは Forge の「記録して届ける」文化で緩和し、**強制 UI にはしない**。

### 3. Forge 正式機能として 5年後も耐えられるか

| 要素 | 5年判断 |
|------|---------|
| 案A 単体・通知のみ | **△** モデル/コスト/信頼リスク |
| **voice↔update リンク DB 正本 + 三層 UX** | **◎** AI はマッチャーとして差し替え可能 |
| 案B 単体 | **△** 個人帰属が弱く差別化不足 |
| 案C 単体 | **○** 補助機能として長寿命。コアにはならない |
| バッジ・採用率 | **×** out-of-scope |

### 4. 必要 DB

**正本（必須）**

```text
voice_adoptions
  voice_response_id, devlog_id, project_id, published_version
  player_quote, update_summary, confidence, model, created_at

player_nurture_events（レジャー用）
  user_id, project_id, event_type
  (voice_submitted | update_published | adoption_linked | replay_on_new_version)
  ref_id, version_key, created_at
  visible_copy（プレイヤー向け短文）
```

**補助（推奨）**

```text
update_voice_themes（案C）
  devlog_id, theme_label, source（ai_aggregate）, display_order

voice_clusters（案B）
  project_id, version_key, cluster_label, member_count
  （個人 ID は通知時のみ参照。公開しない）
```

**既存活用**: `project_voice_responses`, devlogs, `user_notifications`, 追跡（watch）

### 5. 必要 AI 処理

| 処理 | タイミング | 出力 |
|------|-----------|------|
| **採用マッチ** | devlog/新版公開 | related, confidence, player_quote, update_summary |
| **テーマ抽出** | 同上 | 案C 用 3〜5 テーマ（匿名） |
| **クラスタラベル** | 版ごとバッチ | 案B 用（任意） |
| **embedding 事前フィルタ** | 量増後 | 候補ペア削減 |

**重要**: AI の成果物は **DB に保存**し、UI は保存結果を読む。再推論しない。

### 6. 推定コスト

（`docs/player-voice-adoption-ai-design-review.md` と同根）

| 規模 | 月次目安 |
|------|---------|
| 初期 | $0.05〜0.15 |
| 成長期（devlog 100/月） | $0.5〜1.5 |
| 大規模 | $5〜15（embedding 必須） |

**コストより品質リスクの方が大**。Forge コア体験のボトルネックは金額ではない。

### 7. 誤判定時の UX

**原則: 誤って「育てた」と言うより、言わない方がマシ。**

| 種類 | UX |
|------|-----|
| **偽陽性**（言わない方がよかった） | 致命的。静かな「関連の取り消し」+ 内部ログ。プレイヤーへの謝罪通知は**しない**（注目を増やす） |
| **偽陰性**（言ってほしかった） | P1「前回プレイ後の更新」+ D-1 レジャー「更新あり（未リンク）」で緩和 |
| **プレイヤー申告** | 「この関連は違う」1タップ → フィードバック DB（開発者に見せない）→ モデル改善。手動採用フローには接続しない |
| **文言** | 「〜されました」は confidence 高のみ。中間は「今回の更新は、あなたの回答 "…" と関連がある可能性があります」— **正式版は高 confidence のみ通知** 推奨 |

## 「AIで通知できるか」ではなく「コア体験として成立するか」

### 成立条件チェックリスト

| # | 条件 | 現状 | A+三層後 |
|---|------|------|---------|
| 1 | プレイヤーが**自分の言葉**を思い出せる | △ 送信直後のみ | ◎ レジャー + 引用 |
| 2 | **変化**が版単位で分かる | ○ P1 更新 UI | ◎ |
| 3 | **因果**（声→変化）が示される | × | ◎ A |
| 4 | **検証**（再プレイ）に導線 | △ CTA のみ | ◎ D-2 |
| 5 | **継続**（2周目以降も育ててる） | × | ◎ D-1 |
| 6 | 開発者手動なし | ○ | ○ |
| 7 | Steam と差別化 | △ 更新は見える | ◎ 共創の記録 |

**通知は Layer 1 のトリガーに過ぎない。**  
**コア体験 = 因果の可視化 + 関係の継続 + 再プレイでの確認。**

## 現行 UI 再レビュー（Studio / マイページ / 作品詳細）

### プレイヤーが「育成参加感」を得られる接点（現状）

| 接点 | URL / コンポーネント | 参加感 | 問題 |
|------|---------------------|--------|------|
| プレイ後 overlay | `PostPlayVoiceOverlay` | ◎ 入口 | 出口が弱い |
| 初声フォーム | `GameVoiceSection` | ◎ | 完了後「届きます」で終端 |
| サイドバー | `GameDetailSidebar` voice_complete | △ | ✓ 表示のみ。**次に何が起きるか不明** |
| みんなの声 | `EveryonesVoiceSection` | △ | **匿名集計**。帰属なし |
| 更新追跡 | `GameWatchButton` | ○ | 受動 |
| 前回プレイ後の更新 | `MyPageUpdatesSection` | ○ | **何が変わったか**は P1 で改善。**なぜ変わったか（自分）** はなし |
| これまでの更新 | `GameProjectHistorySection` | △ | 開発者更新ログ。**自分の声なし** |
| 通知 | `/notifications` | △ | 新版/devlog。**voice_adopted なし** |

### Studio（開発者）— プレイヤーからは見えない

- P0 フェーズパネルは **開発者の工程整理** として正しい
- プレイヤー側に **鏡像フェーズ（D-3）** がないため、開発者が進めてもプレイヤーは「待ち」しかない
- Studio の voice 集計は **開発者向け**。プレイヤーの「俺の1票」感には接続されない

### 現在の UI でコア体験は成立しているか

**NO。**

- ループは **プレイ → 回答 → 更新を見る → 再プレイ** まで**形**はある
- **「自分の声で変わった」** の接点が **ゼロ**
- P1 は「変化を見る」の**情報品質**を上げたが、**帰属**は未着手
- 回答送信後の copy がまだ「開発の歩みで確認」（`GameVoiceSection`）— P1 と不整合

### 不足している接点（優先順）

1. **個人の voice 履歴 × 更新のリンク表示**（D-1 / A）
2. **回答送信後の「次は更新を待つ」状態 UI**（D-3）
3. **新版再プレイ時の personal hook**（D-2）
4. **voice_adopted 通知**（A のトリガー）
5. **作品詳細の匿名テーマ**（C — 差別化の土台）

### AI 採用通知以外に育て実感を生む方法

| 方法 | 効果 | 自動化 |
|------|------|--------|
| **レジャー（D-1）** | 高 | ◎ |
| **再プレイ hook（D-2）** | 最高 | ◎ A 連動 |
| **待ち状態の可視化（D-3）** | 中 | ◎ voice 送信イベント |
| **初声完了のコピー改善** | 中 | ◎ 文言のみ |
| **追跡中 + 「あなたの回答済み」バッジ** | 低〜中 | ◎ |
| **みんなの声グラフの個人ハイライト** | NG | 個別回答非公開のため不可 |

**通知だけに頼る設計は不可。** レジャー + 再プレイがコア。

## 7. 実装優先順位（GO 後・2026-06-16 オーナー確定順）

**事実 → 体験**。レジャー先行は NG。正本: `docs/voice-adoptions-canonical-design-review.md`

| Phase | 内容 |
|-------|------|
| **1** | `voice_adoptions` + AI マッチ基盤（**通知・UI なし**） |
| **2** | プレイヤー向け「あなたの声が反映された更新」表示 |
| **3** | 再プレイ導線 — **「俺が育てた」発生点** |
| **4** | 育成履歴（レジャー）— adoptions 積み上げの VIEW |

旧「レジャー → 通知」順は **撤回**。

## オーナー判断用 — 推奨 GO パッケージ

**GO するなら「案A + D-1 + D-2」を1テーマで。**  
案C は同梱可。案B は後追い。手動採用 UI は入れない。

**GO 前に決めること**

1. confidence 閾値（推奨 0.80 — 0.75 より誤通知回避優先）
2. 偽陰性の許容 — 「更新は見えるが、育てたとは言わない」ケース
3. レジャーをマイページ中心 vs 作品詳細中心
4. 「〜されました」の断定を使うか（高 confidence のみ YES 推奨）
