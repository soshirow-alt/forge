# 確認依頼 / 変化チェック — 設計正本

**版**: 2026-06-26（オーナー / GPT 設計整理）  
**ステータス**: 設計 GO（実装は段階的）  
**関連**: `docs/forge-principles.md`（増幅：変化を見る → 再プレイ）、`docs/version-published-loop-design.md`（現行の版公開通知・バナー）、`docs/forge-p0-improvement-loop-plan.md`（上位3課題・版公開）

---

## 0. 一言で言うと

Forge が作るべきものは単なる「再プレイ通知」ではなく、**確認依頼 / 変化チェック**である。

ただし **開発者への入力強制はしない**。  
Devlog / 新ver公開は未入力でも可能。入力されたときだけ、通知・マイページ・ゲーム詳細・コミュニティで、より具体的な変化チェック導線になる。

> 開発者に正しい運用を強制するのではなく、  
> 開発者がプレイヤーへ伝えたいことを、より伝わりやすくする。

---

## 1. 用語（内部概念 / ユーザー向け文言）

| 内部概念 | 英語（コード・DB 用の候補） | ユーザー向け優先文言 | 意味 |
|----------|---------------------------|---------------------|------|
| **確認依頼** | `confirmation_request` | 確認依頼 / 今回見てほしいこと | 開発者が任意で付ける補助情報。Devlog / 新ver公開にぶら下がる |
| **変化チェック** | `change_check` | 変化を確認する / 前回からの変化を見る | プレイヤー側に見える表示・CTA。確認依頼の有無で具体度が変わる |
| **前回遊んだverとの差分** | `prior_played_version` | 前回遊んだ版から更新があります | プレイヤーのプレイ履歴と現行 `playable_version` の関係 |
| **変更内容起点** | `change_item` | （表示は自然文） | ターゲティング・表示理由の中心。プレイヤー分類ではない |
| **任意入力** | `optional_hint` | 入力ヒント（ツールチップ） | 必須バリデーションなし。空でも公開可 |

**避けるユーザー向け文言**: とにかく再プレイ / もう一度遊んで / あなたのFBが採用されました（自動断定）

**推奨 CTA**: 変化を確認する / 今回の確認ポイントを見る / このverを試す / 5分だけ確認する / 前回からの変化を見る

**原典との関係**: `forge-principles.md` の「変化を見る → 再プレイ」は**増幅**。本設計はその増幅を「全員への再プレイ呼び戻し」から「必要な人への確認依頼」へ具体化する。

---

## 2. 基本構造

```
開発ログ / 新ver公開（必須フロー・未入力でも公開可）
　└ 任意：確認依頼（confirmation_request）
　　　└ プレイヤー側：変化チェック（change_check）
```

### 2.1 開発ログ / 新ver公開

- 基本機能。タイトル・本文など既存フローは維持
- **確認依頼なしでも公開可能**（新規必須項目を増やさない）

### 2.2 確認依頼（開発者・任意）

開発者が折りたたみ等で追加できる補助情報。例：

| 項目 | 必須 | 例 |
|------|------|-----|
| 今回変わったこと | 任意 | ボス戦の難易度を調整 |
| 今回見てほしいこと | 任意 | 前より理不尽に感じないか |
| 所要時間 | 任意 | 5分 / ステージ1だけ |
| 対応した課題 / FBクラスター | 任意 | Studio「次に直すこと」・FBクラスターと紐付け |
| 誰に見てほしいか | 任意 | 下記 §4 |
| 通知するか / 履歴だけ | 任意 | 通知オフ選択可 |

### 2.3 変化チェック（プレイヤー）

**確認依頼あり**（例）:

> ボス戦の調整が入りました。  
> 5分ほど遊んで、前より理不尽に感じないか確認してほしいそうです。

**確認依頼なし**（例）:

> 前回遊んだ版から、新しい開発ログ / 新verが公開されています。

## 3. 設計方針（従来との差）

| 従来（甘い） | 本設計 |
|-------------|--------|
| 新verが出た → 全員に再プレイ | 今回の変更について、関係するプレイヤーに確認してほしいことを届ける |
| watch ユーザーへ一律通知 | 変更内容・課題紐付け・対象者選択（すべて任意） |
| 「もう一度遊んで」CTA | 「変化を確認」「5分だけ確認」等 |

開発者によっては Discord で完結・細かい説明不要・身内向け・通知不要、などが普通にある。**強制運用にしない**。

### 3.1 開発者 UI — 任意ヒント・折りたたみ

- 公開画面の冒頭から重いフォームを並べない
- 折りたたみ例: 「プレイヤーにもう一度触ってほしい場合」
- ボタン例: 確認依頼を追加 / プレイヤーへのお願いを書く / 変化チェックを設定
- **入力しないと公開できない設計にしない**
- **必須バリデーションをかけない**

### 3.2 ヒントワッペン（入力補助）

常時長文説明は出さない。ラベル横に軽い「入力ヒント」ワッペン → ホバーでツールチップ。

| ラベル | ツールチップ要旨 |
|--------|-----------------|
| 今回変わったこと | 1〜3個で十分。例：ボス調整 / チュートリアル追加 |
| 今回見てほしいこと | 確認観点を書くとFBの質が上がる |
| 所要時間 | 戻りやすくなる。例：5分だけ |

制約: 説教っぽくしない / 画面を重くしない / 必須にしない。

## 4. 変更内容起点のターゲティング

プレイヤーを「見届け中 / FBした / コミュニティ参加」等で**単純分類するだけでは不十分**。  
ロジックの中心は **変更内容（と紐づく課題・FBクラスター）**。

```
1. 今回の変更項目
2. 関連する課題 / FBクラスター（任意紐付け）
3. その課題に関係したプレイヤー
4. 確認依頼 or 変化チェックを届ける（対象者選択が空ならデフォルトルール）
```

### 4.1 誰に見てほしいか（任意・候補）

- 前verを遊んだ人
- 関連FBを送った人
- 見届け中の人
- コミュニティ参加者
- 保存している人
- 全員
- **通知しない（履歴だけ残す）**

### 4.2 表示理由は最大 1〜2 個

複数条件該当でも全部並べない。優先順位：

1. 開発者が今回見てほしいこと（確認依頼本文）
2. その人のFB / 同趣旨FBに関連する変更
3. 前回遊んだverとの差分
4. 見届け中 / コミュニティ / 保存などの関係性
5. 汎用通知

表示例:

> ボス戦の調整が入りました。  
> 前回多かった「理不尽に感じる」というFBを受けた変更です。  
> 開発者は、5分ほど遊んで「前より納得感があるか」を確認してほしいそうです。

## 5. 「あなたのFBが採用されました」の表現レベル

| レベル | 文言 | 条件 |
|--------|------|------|
| L1 安全 | 前回遊んだ版から変更があります | デフォルト |
| L2 やや個別化 | あなたが送ったFBと近いテーマの改善があります | テーマ・クラスター一致（自動は慎重） |
| L3 明確な採用 | あなたのFBが改善に活かされました | **開発者が明示紐付けした場合のみ** |

AI・ルール判定だけで L3 断定しない。`voice_adoptions` 自動マッチャーは L2 以下または開発者確認後に限定（`docs/player-nurture-core-experience-design-review.md` と整合）。

---

## 6. 表示場所

| 場所 | 確認依頼なし | 確認依頼あり |
|------|-------------|-------------|
| **通知** | devlog / 新ver 汎用 | 確認依頼付き（対象者のみ） |
| **マイページ** | 変化があった作品 | 確認依頼が届いている作品 |
| **ゲーム詳細** | 前回verから更新あり | 確認ポイント・所要時間・対応課題・CTA |
| **コミュニティ** | Devlog 引用のみ可 | 確認依頼を起点とした開発者投稿（プレイヤーは返信中心） |

---

## 7. 開発者の懸念（買ってくれないリスク）

短編・ストーリー・謎解き・一度で満足・有料販売予定などでは、何度も無料プレイを促さない。

Forge のメッセージ:

> 必要な範囲だけ、必要な人に、必要な観点で確認してもらう

为此に必要:

- 対象者選択
- 確認依頼の終了条件（将来: 反応数・締切 — 初期は任意）
- 通知しない / 履歴だけ
- Steam / itch.io / ウィッシュリスト導線（既存外部リンク活用）

## 8. 現行実装との差分（2026-06-26 時点）

| 観点 | 現状 | 本設計との差 |
|------|------|-------------|
| Devlog / 新ver公開に確認依頼の任意入力 | **なし**（タイトル・本文・任意の版 bump のみ） | 折りたたみセクション + 任意フィールド群が必要 |
| 入力なしでも公開 | **可**（版 bump ON 時のみ版名必須） | 整合。確認依頼は追加必須にしない |
| 「次に直すこと 上位3」と公開の紐付け | **なし**（`lib/top-priorities.ts` は Studio 表示のみ） | 公開時に任意で priority / クラスターを選択 |
| FBクラスター / priority / feedback と変更項目の紐付け | **なし**（voice_adoptions は AI 事後マッチのみ） | 開発者明示紐付け + 任意のクラスター参照 |
| 通知に確認依頼 | **なし**（`devlog` / `version_published` が watch 全員へ固定） | 対象者選択・通知オフ・確認依頼本文の差し込み |
| マイページ「変化あり」「確認依頼あり」 | **一部**（`mypage-updates-section` は watch 限定・汎用見出し・「もう一度プレイする」） | プレイ済み全般・確認依頼フラグ・文言刷新 |
| ゲーム詳細「前回verからの変化」 | **一部**（`NewPlayableVersionBanner` は watch + 旧版FBあり条件・再プレイ寄り文言） | 確認ポイントカード・所要時間・課題表示 |
| コミュニティで Devlog 引用の確認依頼 | **一部 mock**（`devlogQuote` のみ・確認依頼型ではない） | 確認依頼メタデータ付き開発者起点投稿 |
| 強制入力の発生 | **なし**（devlog タイトル・本文は必須＝既存。版 bump 時版名必須） | 確認依頼項目は必須化しない |

### 8.2 旧設計ドキュメントとの関係

`docs/version-published-loop-design.md` は **watch 全員への版公開通知 + 再プレイバナー** を記述。本書はその上位概念。実装移行時はバナー・通知を「変化チェック」へ段階的に置き換え、watch 限定条件の見直しを含む。

## 9. 実装分割案（mock → 実データ → DB）

**原則**: preview / docs / UI mock は Cursor 単独で可。**DB migration・本番 deploy・main merge はオーナー GO 後**。

### Step 1 — 用語・UI mock（Devlog 公開画面）

- `devlog-new-page.tsx` に折りたたみ「確認依頼を追加」
- 任意フィールド（変わったこと / 見てほしいこと / 所要時間）+ ヒントワッペン
- **local state のみ**。未入力でも投稿可。既存 `addDevlog` シグネチャは触らない or optional 引数を無視

### Step 2 — ゲーム詳細「変化チェック」カード（mock） — **完了（preview）**

- `components/game-change-check-card.tsx` — パターンA（確認依頼あり）/ B（なし）
- 配置: ヒーロー・プレイCTAの**下**、タブの上（初見の主役を侵さない）
- 表示条件: 前回プレイ済み（`hasPlayedGame`）または preview `?returning=1`
- 確認URL: A `/games/seikat-no-tabiji?returning=1`、B `/games/roshin-no-zanko?returning=1`、非表示は `returning` なし

### Step 3 — マイページ「確認依頼あり」表示（mock）

- `mypage-updates-section.tsx` に確認依頼バッジ・headline 分岐（fixture）
- watch 以外の「前verプレイ済み」も将来含める旨をコメント

### Step 4 — 通知コピー・カテゴリ（mock / 表示のみ）

- `lib/notifications.ts` に `confirmation_request` type の表示ラベル案を追加（insert はまだ）
- 通知一覧で fixture 1件表示（開発用フラグ）

### Step 5 — Studio 公開フロー統合

- 版公開パネル（`project-release-studio-panel` 等）からも同じ任意 UI を共有コンポーネント化
- 上位3からの「この課題に対応した」を任意ピック（まだ DB なしなら ID を local に保持）

### Step 6 — DB / Supabase 永続化（**要オーナー GO**）

候補スキーマ（案）:

```text
confirmation_requests
  id, devlog_id, project_id, published_version nullable
  changes_summary text nullable      -- 今回変わったこと
  ask_summary text nullable          -- 今回見てほしいこと
  estimated_duration text nullable
  notify_audience jsonb nullable     -- 対象者選択
  notify_enabled boolean default true
  linked_priority_ids jsonb nullable
  developer_linked_voice_ids uuid[] nullable  -- L3 明示のみ
  created_at

-- 通知拡張: user_notifications に confirmation_request_id nullable
-- or type = 'confirmation_request'
```

- ターゲティング RPC（変更内容 → プレイヤー集合）は Step 6b で分割
- `voice_adoptions` 自動マッチャーとの役割分担を文書化してから接続

### Step 7 — コミュニティ本番接続（**要 GO**）

- 開発者投稿時に `confirmation_request` を引用
- プレイヤー返信中心 UI（既存コミュニティ方針と整合）

### Step 8 — ターゲティング・終了条件（P1）

- 反応数・締切
- FBクラスター自動参照（`voice_clusters` 等 — `player-nurture-core-experience-design-review.md` 補助テーブル）

## 10. やらないこと（設計 NG）

- 入力しないと Devlog / 新ver 公開できない
- 何度も全員に遊ばせる前提の UX / コピー
- AI・ルールだけで「あなたのFBが採用されました」と断定
- プレイヤーを雑なセグメントラベルで羅列
- 公開画面に常時長い説明文・必須フォームを並べる

---

## 11. 目指す体験（再掲）

> 開発者が変更を加えたとき、  
> その変更を確認するのに適したプレイヤーへ、  
> 短く・具体的な依頼を出せる。  
> ただし、それは強制ではなく、開発者が必要に応じて使える補助機能である。

プレイヤーは「自分がゲームを育てている」と感じ、開発者は「必要な確認が取れた」と感じる。
