# P1-2.7 本番 UX レビュー — UI ブラッシュアップ案（A/B/C 比較）

**ステータス**: オーナーレビュー用（**実装 GO 前**）  
**前提**: P1-2.7 deploy 済み（`dpl_HjmzgtqxKEwePqKqohGN2Q7s7miY`）。方向性 GO、**完成ではない**。

**コード変更**: なし。UI 案のみ。

---

## 0. オーナー所感（整理）

| 良くなったこと | まだ弱いこと |
|---|---|
| FB 一覧 → 作品育成画面へ近づいた | 「状態管理 UI」感が残る |
| 5 段サイクル + Hero + Rail | **今** と **次** が同强度 → 何を押せばいいか迷う |
| FBを読む が独立 | Forge の最重要 **「次の行動」** が主役になっていない |

**Forge の優先順位**

```
次の行動  ≫  現在地
```

---

## 1. 問題の核心（本番所見）

### 1-1. 視覚的競合

現状（改善中フェーズの例）:

```
Hero:  次にやること / 開発ログを書く     ← 大きい
Rail:  [✓読] [今·改善中] [次·devlog] ...  ← 「今」「次」バッジ + ring が Hero と競合
Primary: 開発ログを書く                   ← Hero と同文言で3重
```

開発者の視線が **Hero / Rail次 / Primary** に分散する。  
Rail の「今」と「次」が **同じオレンジ系・同サイズ帯** のため、**状態説明 UI** に見える。

### 1-2. 文言（改善中 vs 改善する）

| 観点 | 改善中 | 改善する |
|---|---|---|
| 状態モデル | ◎ 自然（devlog までの期間） | △ イベントに見えがち |
| 初見理解 | △ 抽象的（今何をする？） | ◎ 動詞で行動が想像できる |
| 解決策 | **内部 `improving` / UI 文言を分離** | UI=`改善する`、状態は `improving` のまま |

---

## 2. 内部状態 vs UI 表示（共通方針）

**変更しない（内部）**

```typescript
NurtureStepId: "read" | "improving" | "devlog" | "publish" | "wait"
NurtureDataPhase, feedbackRead, buildNurtureDisplayContext ...
```

**変更候補（UI のみ）**

| stepId | 案A UI | 案B UI |
|---|---|---|
| improving | 改善中 | **改善する** |
| read | FBを読む | FBを読む |
| devlog | 開発ログを書く | 開発ログを書く |
| … | … | … |

状態モデルは v2 のまま。**ラベルと視覚階層だけ**ブラッシュアップ。

## 3. 三案概要

| 案 | Rail ラベル | 「今」表示 | Rail の役割 | 一言 |
|---|---|---|---|---|
| **A** 現状維持 | 改善中 | あり（今バッジ） | 5 段フル + 今/次 | モデル正確、初見弱い |
| **B** 改善する | 改善する | あり（今バッジ） | A と同構造、文言のみ変更 | 理解性↑、競合は残る |
| **C** 次アクション中心 | 改善する* | **なし or 極小** | 位置ドット + Hero 主役 | 次最優先、現在地は副 |

\* 案 C でも内部は `improving`。Rail 上は短縮 `改善` or アイコンのみ可。

## 4. 案 A — 現状維持（改善中）

### ワイヤ（改善中フェーズ）

```
┌─ 作品カード ─────────────────────────────────────┐
│  次にやること                                      │
│  開発ログを書く                         text-2xl   │
│  改善が終わったら記録しましょう                    │
│                                                    │
│  [✓FB] → [今·改善中] → [次·devlog] → [○] → [○]   │
│           orange        ring・大                     │
│                                                    │
│  [ 開発ログを書く ]                                │
└────────────────────────────────────────────────────┘
```

### 評価

| 観点 | 評価 | コメント |
|---|---|---|
| **初見理解性** | △ | 「改善中」だけでは次の操作が不明。Hero に依存 |
| **複数作品一覧** | ○ | 5 chip 並列で位置比較は可能。ただし今/次が作品ごとに散る |
| **2 周目以降** | ○ | ↺ + リセットは機能。文言「改善中」は周回でも同じで単調 |
| **モバイル** | △ | 5 chip + 今/次バッジで詰まる。Hero が埋もれやすい |

**長所**: 状態モデルと UI が一致、説明不要。  
**短所**: オーナー指摘どおり **今≈次** の競合。完成度には届かない。

## 5. 案 B — 改善する（文言差替 + 現構造）

### ワイヤ

```
┌─ 作品カード ─────────────────────────────────────┐
│  次にやること                                      │
│  開発ログを書く                         text-2xl   │
│  改善が終わったら記録しましょう                    │
│                                                    │
│  [✓FB] → [今·改善する] → [次·devlog] → [○] → [○] │
│                                                    │
│  [ 開発ログを書く ]                                │
└────────────────────────────────────────────────────┘
```

**追加ブラッシュアップ（B+ 推奨）** — 文言だけでなく軽い視覚差:

| 要素 | 変更 |
|---|---|
| 今 chip | サイズ **小**、バッジ「今」**非表示 or zinc のみ** |
| 次 chip | Hero と **同文言禁止** — Rail 次は `→ devlog` 等の短ラベル |
| Hero | **唯一の「次」文案** — text-3xl、Rail 次は位置のみ |

### 評価

| 観点 | 評価 | コメント |
|---|---|---|
| **初見理解性** | ○ | 「改善する」で Unity 等に向かうイメージ。「devlog」は Hero で足りる |
| **複数作品一覧** | ○ | Hero 行 Y 揃えで「次: 開発ログを書く」スキャンしやすい |
| **2 周目以降** | ○ | 「改善する」は毎周同じ動詞で繰り返し理解しやすい |
| **モバイル** | △〜○ | B 単体では A と同じ詰まり。B+ 視覚差で Hero が浮く |

**長所**: 実装コスト小（ラベル + スタイル）。内部状態そのまま。  
**短所**: 構造上 **今/次 2 軸** は残る。B+ しないと競合解消不完全。

## 6. 案 C — 次アクション中心（改善中 chip を弱体化）

### コンセプト

- **Hero + Primary = 次の行動の唯一の主役**
- Rail = **進捗レール**（どこまで来たか）。**今バッジ廃止**
- `improving` 期間中も Rail 上の強調は **次ステップ 1 点のみ**（または Hero のみ）

### ワイヤ C-1（コンパクトレール — 推奨）

```
┌─ 作品カード ─────────────────────────────────────┐
│                                                    │
│  開発ログを書く                          text-3xl  │  ← 「次にやること」ラベルも省略可
│  改善が終わったら記録しましょう          text-xs    │
│                                                    │
│  [ 開発ログを書く ]                      Primary   │
│                                                    │
│  ✓FB  ✓改善  ●devlog  ○公開  ○待    サイクル2 ↺  │
│  gray gray  ^次のみ小ring   点      点             │
└────────────────────────────────────────────────────┘
```

- `●devlog` = 次の位置（小さな dot + 細 ring）。**文案は Hero のみ**
- `✓改善` = 完了（FB 読了後は改善フェーズを「通過」扱いにするか、読了=改善開始で ✓FB のみ）

**改善フェーズの位置表示（2 パターン）**

| C-1a | FB 読了後: `✓FB · 改善中··· · ○devlog` — 改善は **進行中ドット**（pulse なし、zinc 小文字） |
| C-1b | FB 読了後: `✓FB · ○dev` — **改善ステップを Rail から省略**。Hero 補助行「いま改善中」 |

### ワイヤ C-2（一覧特化 — 複数作品）

```
作品A   開発ログを書く              [ 開発ログを書く ]
        ✓ ✓ ● ○ ○

作品B   FBを読む                    [ FBを読む ]
        ● ○ ○ ○ ○

作品C   反応を待つ                  [ 作品ページを確認する ]
        ✓ ✓ ✓ ✓ ●
```

**0.3 秒スキャン**: 左端=作品名、**1 行目=動詞のみ**、2 行目=レール、3 行目=ボタン。

### 評価

| 観点 | 評価 | コメント |
|---|---|---|
| **初見理解性** | ◎ | 迷いは「大きい動詞 + ボタン 1 つ」だけ |
| **複数作品一覧** | ◎ | 次アクション 1 行比較が最も容易 |
| **2 周目以降** | ○ | レールリセット + ↺。過去は折りたたみのまま |
| **モバイル** | ○ | 5 短 dot / チェックで 1 行収まる |

**長所**: オーナー要望「次 > 今」に最も忠実。状態管理 UI 感が薄れる。  
**短所**: 「いま改善中」の文脈は Hero 補助行 or パネル click に依存。Rail だけでは **現在地** がやや弱い（意図的トレードオフ）。

## 8. 「改善中」vs「改善する」— 初見ユーザー向け比較

**シナリオ**: 初めて `/my-projects` を開いた開発者。FB 読了直後。

| 質問 | 改善中（A） | 改善する（B） |
|---|---|---|
| 今何をすべき？ | 「開発ログを書く」（Hero）と「改善中」（Rail）が両方見える → **どちらが本題？** | Hero「開発ログ」+ Rail「改善する」→ **順序**（先に改善→後で記録）が想像しやすい |
| ボタンは？ | Primary=devlog だが Rail にも「次·devlog」 | 同左。B+ で Rail 次を弱めれば解消 |
| 初見 3 秒 | 「状態を説明されている」 | 「やることが並んでいる」 |

**結論（初見のみ）**: **UI 文言は「改善する」優位**。内部 `improving` は維持。

## 9. Cursor 推奨

### 第一推奨: **案 C-1b + UI 文言 B**

- 内部: `improving` 維持
- UI ラベル: パネル・補助行では「改善する / 改善中」使い分け可
- Rail: **今バッジ廃止**、**次は dot のみ**、**文案は Hero 独占**
- Hero: `開発ログを書く` text-3xl、補助 `いま改善中 · 終わったら記録`
- Primary: Hero と同ラベル（1 つ）

### 第二推奨: **案 B+**（C が大きい場合の最小差分）

- ラベル `改善する` に変更
- 「今」バッジ削除 + 今 chip 20% 縮小
- Rail「次」chip から長文案削除（`devlog` 短縮のみ）
- Hero を card 幅の 60% 以上の視覚重量に

### 非推奨: **案 A そのまま**

- 方向性は正しいが、オーナー FB「完成ではない」に合致。維持のみでは不十分。

## 10. オーナー判断ポイント（GO 前）

1. **採用案**: A / B / B+ / C-1a / C-1b のどれか
2. **Rail から「今」バッジ**: 廃止 GO か（C 前提）
3. **Hero ラベル「次にやること」**: 残す / 省略（C-1 では省略可）
4. **改善フェーズの Rail**: C-1a（小さく改善表示）vs C-1b（Rail から省略）
5. **UI 文言**: 改善する（推奨）vs 改善中（補助行のみ）
