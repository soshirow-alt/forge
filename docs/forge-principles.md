# Forge Principles（Forge プロダクト原典）

この文書は Forge **プロダクト体験**の判断正本です。  
事業・マネタイズ仮説は `docs/forge-business-hypothesis.md` を参照。

本書は現時点で最も有力な初期仮説の結晶であり、より強い仮説が検証された場合はオーナー判断で更新する。  
意味の変更はプロダクトオーナーの明示的な指示がある場合のみ行います。  
実装者（人間・AI）は整理・参照はしてよいが、**勝手に改変しない**こと。

---

## 1. Forge原典

### 一言で言うと

**Forge は、完成前のゲームとプレイヤーを繋ぐプラットフォーム。**

### Steam との違い

| | Steam | Forge |
|---|--------|--------|
| タイミング | 完成したら来てね | **完成してなくていいよ** |
| 主役 | 完成品の販売・配信 | **開発中ゲームの発見と成長** |

### 開発者への価値

- 作ったゲームを**見つけてもらえる**
- 作ったゲームを**遊んでもらえる**
- 作ったゲームに**感想（改善材料）が返ってくる**

### プレイヤーへの価値

- まだ世に出ていないゲームを**遊べる**
- **無料で**遊べる（MVP の前提）
- ゲームの**成長を見られる**
- 未来のヒット作を**先に発掘できる**

### Forge は何ではないか

- **テスター募集サイトではない** — テスト参加は手段の一つ
- **ゲーム紹介・送客サイトではない** — プレイと反応が Forge 上に残ることが重要
- **完成品ストアではない** — Steam の前段階

Forge は **ゲームが成長する場所**。

### コア体験（学習ループ）

**開発者・プロダクト全体（コア）**

```
投稿
  ↓
発見
  ↓
プレイ（当該版）
  ↓
初声（版に紐づく）
  ↓
次に直すことの決定
  ↓
改善・版公開・Devlog
  ↓
次版 ──→（ループ継続）
```

**プレイヤー視点（コア）**

```
発見
  ↓
プレイ
  ↓
声を届ける（初声）
```

**増幅（コアではないが、あれば価値が大きく上がる）**

```
〔プレイヤー〕変化を見る → 再プレイ
〔横断〕見届け人（同一作品の継続追跡）
```

- **学習ループのコア**は「発見→プレイ→初声」と「開発者の次版」まで。
- 「変化を見る」「再プレイ」「見届け人」は**価値増幅装置**。いなくても開発者向けの学習ループ価値は成立しうる。
- プレイヤーには **改善** が **変化を見る** として現れる（devlog・新版・参考にした声など）。
- 新機能・UI変更・データ設計は、**学習ループ（コア）** と **増幅要素** のどちらを強化するかで判断する。

### 見届け人（価値増幅）

**定義**: 同一ゲームを継続して追うプレイヤー。

- Forge の**必須条件ではない**
- いると「変化を見る」「再プレイ」が起きやすく、開発者・プレイヤー双方の価値が上がる
- 件数競争・「最多見届け人」ランキングは作らない
- tier 設計: `docs/witness-tier-design-review.md`

### プレイヤーサイクル（正式定義）

プレイヤー体験は **5 段**で記述する（コア 3 段 + 増幅 2 段）。

| 段 | 意味 | 完了の目安 | 位置づけ |
|----|------|-----------|----------|
| **発見** | 完成前のゲームと出会う | 作品詳細に到達 | **コア** |
| **プレイ** | プレイ可能版を遊ぶ（ログイン必須） | プレイ記録が残る | **コア** |
| **声を届ける** | この版について Forge に返答を残す | **初声完了**（問いへの返答が 1 件以上） | **コア** |
| **変化を見る** | ゲームの育ちを確認する | devlog・新版等を認知 | **増幅** |
| **再プレイ** | 新版で再度プレイし、サイクルに再突入 | 新版でのプレイ | **増幅** |

**初回の声**と**2 回目以降の声**は別物として扱う。

| | 主な動機 |
|---|---------|
| **初回** | 熱、低摩擦、問いへの返答、共創参加 |
| **2 回目以降** | 上記に加え **変化を見る**（反映実感、続きの確認） |

**コア・増幅・非コア**

- **コア**（最優先）：発見、プレイ、声を届ける（初声）、開発者の次に直すこと→次版
- **増幅**（あれば価値が大きく上がる）：変化を見る、再プレイ、見届け人、影響力可視化（読まれた・採用された・改善に繋がった）
- **非コア**（段階的でよい）：SDK、閲覧数、高度な分析、経済的インセンティブ（後から追加可）

**Discord との役割分担**

- Discord：**会話・熱・所属** — Forge の代替ではない
- Forge：**版ごとの問い・育成の記録・変化を見る体験** — 完成前ゲームの育成に参加する公式の場

**フォローと初声（別概念）** — 2026-06 原典更新

| | フォロー（機能名） | 初声 |
|---|------|------|
| **意味** | 開発者への好意・期待（概念としての **「応援」**） | 開発者の問いへの返答 |
| **対象** | **開発者**（作品単位ではない） | 作品・版に紐づく声 |
| **性質** | 感情 | 情報（改善判断の材料） |
| **UI** | ボタン **フォロー** / サイドバー **フォロー中の開発者** | 声を届ける |
| **統合** | **しない** — 初声しても自動フォローしない。フォローしても初声扱いにしない |

**廃止**: 作品単位の「応援中」サイドバー・応援ボタン。  
不満・批判・改善要望を伝えたい場合でも、開発者の問いには十分回答し得る。**感情と情報は分離**する。

### ブランドメッセージ

> **まだ誰も知らないゲームを、一緒に面白くする。**  
> 見つけて、遊び、反応を届け、成長を見届けましょう。

### トーン＆ビジュアル

- ダーク基調 × オレンジアクセント
- Steam × Product Hunt × インディーショーケース
- モダン・ポリッシュ・ややワクワク（子供っぽくしない）
- 管理画面っぽい平坦さは避ける

## 2. 判断基準

### 機能を追加・変更するとき

1. **学習ループ（初声→次版）を強化するか？** — 増幅のみの強化は後回し可
2. **原典の意味を変えていないか？** — 変えるならオーナー確認
3. **正式リリース初期版のスコープか？** — `docs/out-of-scope.md` を参照
4. **実装都合で仕様を歪めていないか？** — 技術都合より UX 原典優先
5. **単なる送客になっていないか？** — プレイ・反応・追跡が Forge に残るか

### 正式リリース初期版で含めるもの（2026-06）

- **フォロー** — 開発者単位。概念上の「応援」を UI 上はフォローで表現
- **共感** — 自由記述 FB のみ。投稿数に加算しない。声の重み・集約に反映
- **開発者 FB 評価** — 「開発に役立った」（開発者本人のみ非公開）
- **影響度スコア** — 信頼される見届け人の可視化。投稿数だけで強く評価しない
- **月間影響度ランキング** — 毎月リセット。過去入賞は実績・バッジに残す
- **実績・バッジ** — 活動サマリーではなく、獲得条件・進行状況の画面

### 依然として作らないもの（明示）

- 投げ銭・課金・販売
- 採用率のゲーミフィケーション（「提案採用 ○%」など）
- Forge SDK の**実装**（説明 UI のみ可）
- 新しい収益化機能
- **有料**ランキング・バッジ課金

**注**: 上記「含める」と「作らない」は矛盾しない — **コミュニティ機能のランキング・実績は可**、**金銭課金は不可**。

### 用語方針（ユーザー向け）

| 避ける / 内部 | ユーザー向け |
|---------------|-------------|
| テスター募集中 | **テストプレイ受付中** |
| テスター応募 | **テストプレイに参加** |
| 応援する（連打で数字増） | **フォロー**（開発者・1人1回。投げ銭ではない） |

## 3. ログイン方針

### 基本思想

**「ゲームを見つける」は開放、「プレイする」以降はログイン必須。**

未ログインのまま外部リンクへ飛べると、プレイ履歴・フィードバック・フォロー・見届け・更新追跡が残らず、Forge が送客サイトになる。

### ログイン不要

- トップ（ホーム）を見る
- ゲーム一覧・発見を見る
- ゲーム詳細を見る

### ログイン必須

- プレイする / 外部リンクへ進む
- フィードバックを書く
- フォローする（開発者）
- 見届ける / 更新を追う
- あとで見る（ブックマーク）
- 作品を投稿する
- 通知を見る
- マイページ / ダッシュボード（マイ作品）を見る

### 未ログイン時の UX

- ボタンは**非表示にしない**
- ラベル例：`ログインしてプレイ` / `ログインしてフォロー` など
- 押したら **`/login` へ遷移**（モーダルで阻まない）
- 補足：`ログインすると使えます` / `プレイ後にフィードバックを送れます` 等
- **localStorage でログイン必須アクションを仮保存しない**
- ログイン成功後は **原則 `/` へ**。例外：**プレイ / 外部リンク** から来た場合のみ `?return=/games/{id}` で作品詳細へ戻す（ホワイトリスト検証、無効時は `/`）

### フォローの仕様

- 投げ銭**ではない** — 開発者への感情的応援（概念上の「応援」）を **フォロー** 機能で表現
- **対象は開発者** — 作品単位の応援ボタン・「応援中」一覧は使わない
- **1ユーザー1開発者あたり1回** — フォロー後は「フォロー中」表示
- サイドバー: **フォロー中の開発者**
- 連打で数字が増え続ける仕様は **NG**

## 4. localStorage 方針

### 原則

**本番でユーザー間・端末間で共有されるべき情報は Supabase に保存する。**

localStorage は **下書き・UI状態・デモ用の一時データ** に限定する。

### Supabase に置くべきもの（例）

- ユーザー投稿プロジェクト（`projects`）
- 開発者プロフィール
- フォロー・ブックマーク・見届け（更新追跡）・プレイ履歴
- 構造化フィードバック

### localStorage でよいもの（例）

- フォーム下書き（未実装なら将来用）
- UI の折りたたみ状態
- **デモ・MVP 暫定**：通知、開発ログ、フォロー数、テスター応募数など（移行予定）
- 想定プレイ時間・開発者観点メモ等の **extras**（`forge-game-extras`）— 将来的に Supabase へ移行検討

### 禁止

- ログイン必須アクションの結果を localStorage のみに保存する
- 「とりあえず localStorage」で本番共有データを永続化する

## 5. フィードバック思想

### 位置づけ

フィードバックは**レビューではなく、開発者に返る改善材料**。

「声を届ける」は **5 項目フォームを全部書くこと** ではない。  
プレイヤーサイクル上の **声を届ける** は **2 層**で構成する。

### 声を届ける（2 層）

**1 段目：初声**

- この **プレイ可能版** について、開発者が設定した **問い** のうち、プレイヤーが **1 件以上** 返答を残した状態を **初声完了** とみなす。
- プレイヤーは **0 問・1 問・複数問・全問** すべて自由。回答数の多少は評価しない。強制しない。
- 回答形式の例：選択式、はい/いいえ、3 択、1 行テキスト。
- **「声を届けた」の完了 = 初声完了**（問いへの返答が 1 件以上）。プレイヤー成功体験は **返事を届けた** で完結する。深い改善材料は不要。

**版プレイヤー問い（version_prompt）**

- 開発者は各 **プレイ可能版** に対して、プレイヤーへの問いを **複数** 設定できる（**上限 10 問**）。
- 同一版で複数仮説（チュートリアル、難易度、バランス、UI 等）を検証するのは自然な使い方。
- 旧来の「特に見てほしい観点」（focusNotes）の思想を、**版に紐づく問い** として再定義する。
- 問いが多いほど回答率が下がる可能性がある — 開発者 UI に **注意喚起** を表示する。

**デフォルト問い（開発者が問いを設定しない場合）**

- 開発者が問いを 1 件も設定していない版では、プラットフォーム **デフォルト問い** を提示する。
- デフォルト例：**もう一度遊びたい？**（`would_replay` と整合：もう一度遊びたい / 更新次第また遊びたい / 今はもう遊ばない）
- デフォルト問いも、プレイヤーへの **返答任意**（0 問回答可）。

**2 段目：深い改善材料（任意）**

- 熱量が高いプレイヤー向けの **任意追加**。成功体験には含めない。
- 項目（構造化）：
  - 良かった点
  - 気になった点
  - バグっぽい挙動
  - 自由記述
- 初声完了とは独立。書かなくても **声を届けた** として扱う（初声完了時）。

**公開範囲**

- **個別回答は公開しない** — レビューサイト化を避ける。
- **「みんなの声」** — 集計・傾向のみ公開可。個別の声の一覧ではない。

**みんなの声（プレイヤー向け）**

- プレイヤーは **「みんなはどう感じたか」** を知りたい — **グラフ・件数・比率** 主体でよい。
- 個別回答・ユーザー名・長文引用は **出さない**。
- デモ作品はサンプル表示可。実データ優先。

**みんなの声（開発者向け）**

- 開発者は **次に何を直すか** が伝わる状態を目指す。
- 単なるアンケート集計（例：武器A 41% / 武器B 59% の並列だけ）は **不十分**。
- 望ましい流れ：**数字 → 解釈 → 改善の示唆**。
- 例：「武器Bを好むプレイヤーがやや多いが、A派も4割存在」「チュートリアルは概ね伝わっているが、約3割は分かりづらさを感じている」
- AI 集約は **開発者支援** として導入可。プレイヤー代替・自動返信は NG（§7）。

### 導線（順序が重要）

```
ゲームを理解する
  ↓
プレイする
  ↓
初声（問いへの返答）
  ↓
（任意）深い改善材料
```

詳細ページを開いた直後に「評価して」「コメントして」と**迫らない**。  
プレイ直後は **問いへの短い返答** を優先し、深い改善材料は **折りたたみ・任意** とする。

### ユーザー向け copy の方針

| 避ける | 使う |
|--------|------|
| 評価する、レビューする、アンケート | 返事を届ける、この版について教えてください |
| 改善材料を全部書いて | もっと詳しく伝えたい（任意） |

### 開発者側

- 開発者が**何を採用するかは開発者が決める**
- **問いの中身は開発者が決める** — Forge はゲーム開発の専門家ではない。問いの設定・集計・改善接続を支援する（事業仮説 §7）
- 開発者が **参考になった** 声を評価できる（非公開）。Good レビュアー判定の主体は開発者
- 「ユーザー意見に従え」と見える表現は避ける
- プレイヤー提案採用は**実績として見せてよい**が、義務化しない
- **1 版・最大 10 問** — 問いは版公開の意図とセットで設定する。多すぎる問いは回答率低下の注意喚起を表示
- **回答率・回答数をプレイヤーに評価として見せない**

## 6. マネタイズ仮説

> **現時点は仮説。MVP では収益機能を実装しない。**

### 前提

- プレイヤー体験は **無料** が原典に沿う
- **学習ループが回ること**が最初の価値。課金は無料期間後（事業仮説: `docs/forge-business-hypothesis.md`）

### 将来あり得る方向（未確定・未実装）

1. **開発者向けツール** — 詳細アナリティクス、更新告知、テスター管理の高度化
2. **Forge SDK（任意）** — 匿名プレイデータ（プレイ時間・到達率等）。導入しなくても Forge は使える
3. **露出・プロモーション** — 完成前作品の featured 枠等。**おすすめ順をフォロワー数だけで支配しない**（月間影響度ランキングは別画面）
4. **コミュニティ・支援** — 投げ銭ではなく、**フォロー**（開発者への応援）の延長

### やらないこと（収益化）

- 投げ銭、課金壁、作品販売
- ランキング課金、バッジ課金
- プレイヤーに金銭を払わせる体験

## 7. AI機能方針

### プロダクト内（Forge アプリ）

| 項目 | 方針 |
|------|------|
| AI サムネ生成 | **Coming Soon 表示のみ** — 外部 API は MVP で使わない |
| AI フィードバック要約 | 未実装 — **開発者向け**「みんなの声」の **解釈・改善示唆** 生成に利用可。個別回答の公開は NG（§5） |
| AI による自動返信 | **NG** — 人間のプレイヤーの声を尊重 |
| Forge SDK | AI ではない — 匿名プレイデータ取得の任意機能（将来） |

**AI 集約の位置づけ（開発者向け）**

- 目的：**次に何を直すか** が伝わること。ダッシュボード型の数字並列だけにしない。
- 入力：問い別の集計（件数・比率）。個別回答テキストは開発者のみ参照可。
- 出力：解釈文・改善示唆（例示は §5「みんなの声（開発者向け）」）。
- プレイヤー向け UI では AI 生成文をそのまま出さず、**集計グラフ** を主とする。

### 開発プロセス（ChatGPT × Cursor）

- 仕様の原典は **`docs/forge-principles.md`**
- 現在地（リポジトリ内）は **`docs/forge-handoff.md`**
- 変更履歴は **`docs/forge-changelog.md`**
- **GPT 用メモ形式標準（恒久）**は **`docs/chatgpt-summary-format.md`** — オーナーが変更を明示するまで Cursor は常に従う
- **ChatGPT に貼る差分サマリ**は **`docs/chatgpt-summary.md`**（作業のたびに上書き）
- **新 GPT スレッド初回**は **`docs/chatgpt-handoff.md`**（全量スナップショット）を先に1回貼る
- コピー：`npm run copy-summary` または Cursor 返答末尾の `text` ブロック Copy
- Cursor 作業完了時はサマリをファイル + コードブロックの両方に出力
- UI 変更時は `■ 今回変更した画面`（画面位置含む）を必須。設計判断セクション（なぜこの設計 / 他案 / In Out / リスク / 確認手順）は削らない
- **設計判断が絡む論点**では、サマリに `Cursorの推奨案` / `推奨理由` / `懸念点` を**該当時のみ**追記（各3〜5行）。DB・認証・通知・権限・保存先・拡張性など
- **トリガー運用（恒久）** — `docs/forge-triage-operations.md`
  - **`CURSOR`** のみ → ChatGPT が Cursor 貼付用完成文 1 本（断片禁止）
  - Run/Deploy/Migration スクショ → Run 判断 [A]〜[D]
  - summary / handoff / GPT判断用メモ → レビュー（現在地・リスク・次アクション・原典整合）
  - UX 違和感の発言 → UX レビュー（プロダクトレビュー優先: 原典＞ユーザー＞開発者＞MVP＞技術）
  - ChatGPT の役割はコードレビューではなくプロダクトレビュー

## 8. その他の判断軸

### 発見（Discovery）

- 「次にハマるゲームを**完成前に**見つける」体験を最優先
- Steam ほど複雑なフィルタにしない
- 軸の例：ジャンル、開発フェーズ、想定プレイ時間、テストプレイ受付、プレイ環境

### 詳細ページ

- 「なぜ**今**このゲームを遊ぶべきか」が伝わる情報を上部に
- 開発ログ / 履歴で「育っている感」を出す（v0.1, v0.2…）
- 外部リンク・プレイ URL は明示。安全に関する注意書きを添える

### 変化を見る（プレイヤー）

- プレイヤーは devlog・新版公開・（将来）参考にした声を通じて、**ゲームの育ち**と**自分の返答が育ちに繋がったこと**を確認できる
- **変化を見る** はプレイヤーサイクルの**増幅**。初声で学習ループは始まる。変化を見せると価値が上がる
- リアルタイム返信やチャット機能は必須ではない — **記録として残る成長** が Forge の強み

### データ・インフラ

- 認証・永続データ：**Supabase**
- デプロイ：**Vercel**（想定）
- 日本語 UI。サービス名 **Forge** は英語表記のまま
