# Forge Principles（Forge プロダクト原典）

この文書は Forge **プロダクト体験**の判断正本です。  
事業・マネタイズ仮説は `docs/forge-business-hypothesis.md` を参照。

本書は現時点で最も有力な初期仮説の結晶であり、実装・Preview 確認・オーナー判断で検証された内容を反映して更新する（**原典 v2**）。  
**古い原典に実装を戻すことが目的ではない。** 学習ループ・送客防止・非レビューなどの**芯**は維持する。  
意味の変更はプロダクトオーナーの明示的な指示がある場合のみ行います。  
実装者（人間・AI）は整理・参照はしてよいが、**勝手に改変しない**こと。

---

## 1. Forge原典

### 一言で言うと

**Forge は、完成前のゲームとプレイヤーを繋ぐプラットフォーム。**

### Steam との違い

| | Steam | Forge |
|---|--------|--------|
| タイミング | 完成したら来てね | **完成してなくていいよ** |
| 主役 | 完成品の販売・配信 | **開発中ゲームの発見と成長** |

### 開発者への価値

- 作ったゲームを**見つけてもらえる**
- 作ったゲームを**遊んでもらえる**
- 作ったゲームに**感想（改善材料）が返ってくる**

### プレイヤーへの価値

- まだ世に出ていないゲームを**遊べる**
- **無料で**遊べる（MVP の前提）
- ゲームの**成長を見られる**
- 未来のヒット作を**先に発掘できる**

### Forge は何ではないか

- **テスター募集サイトではない** — テスト参加は手段の一つ
- **ゲーム紹介・送客サイトではない** — プレイと反応が Forge 上に残ることが重要
- **完成品ストアではない** — Steam の前段階

Forge は **ゲームが成長する場所**。

### コア体験（学習ループ）

**開発者・プロダクト全体（コア）**

```
投稿
  ↓
発見
  ↓
プレイ（当該版）
  ↓
初声（版に紐づく）
  ↓
次に直すことの決定
  ↓
改善・版公開・Devlog
  ↓
次版 ──→（ループ継続）
```

**プレイヤー視点（コア）**

```
発見
  ↓
プレイ
  ↓
フィードバック / 反応を届ける（概念上は初声）
```

**増幅（コアではないが、あれば価値が大きく上がる）**

```
〔プレイヤー〕変化を見る → 再プレイ
〔横断〕見届け人（称号・伴走の記録）
```

- **学習ループのコア**は「発見→プレイ→フィードバック（初声）」と「開発者の次版」まで。
- 「変化を見る」「再プレイ」「見届け人」は**価値増幅装置**。いなくても開発者向けの学習ループ価値は成立しうる。
- プレイヤーには **改善** が **変化を見る** として現れる（devlog・新版・参考にした声など）。
- 新機能・UI変更・データ設計は、**学習ループ（コア）** と **増幅要素** のどちらを強化するかで判断する。

### 見届け人（価値増幅・称号）

**定義**: 作品が正式版到達などの条件を満たしたとき、プレイ・フィードバック・更新追跡などの関与に基づき **付与される称号**（`project_witness_grants`）。**ユーザー操作名ではない。**

- **「更新を追う」とは別** — 更新追跡は `project_watches` の行動。見届け人は結果としてのバッジ・人数表示
- Forge の**必須条件ではない**
- いると「変化を見る」「再プレイ」が起きやすく、開発者・プレイヤー双方の価値が上がる
- 件数競争・「最多見届け人」ランキングは作らない
- tier 設計: `docs/witness-tier-design-review.md`

**「見届ける」という言葉**

- **操作名・ボタン名には使わない**（ユーザー向けは **更新を追う**）
- ブランドメッセージ上の比喩（「成長を見届けましょう」）としては許容する

### プレイヤーサイクル（正式定義）

プレイヤー体験は **5 段**で記述する（コア 3 段 + 増幅 2 段）。

| 段 | 意味 | 完了の目安 | 位置づけ |
|----|------|-----------|----------|
| **発見** | 完成前のゲームと出会う | 作品詳細に到達 | **コア** |
| **プレイ** | プレイ可能版を遊ぶ | 登録ユーザー: プレイ記録が残る。ゲスト: 外部リンクのみ（DB 非記録） | **コア** |
| **フィードバック / 声を届ける** | この版について Forge に返答を残す（UI では「フィードバック」） | **初声完了**（開発者の問い、またはデフォルト問いへの返答が 1 件以上） | **コア** |
| **変化を見る** | ゲームの育ちを確認する | devlog・新版等を認知 | **増幅** |
| **再プレイ** | 新版で再度プレイし、サイクルに再突入 | 新版でのプレイ | **増幅** |

**初回の声**と**2 回目以降の声**は別物として扱う。

| | 主な動機 |
|---|---------|
| **初回** | 熱、低摩擦、問いへの返答、共創参加 |
| **2 回目以降** | 上記に加え **変化を見る**（反映実感、続きの確認） |

**コア・増幅・非コア**

- **コア**（最優先）：発見、プレイ、フィードバック（初声）、開発者の次に直すこと→次版
- **増幅**（あれば価値が大きく上がる）：変化を見る、再プレイ、見届け人（称号）、影響力可視化（読まれた・採用された・改善に繋がった）
- **非コア**（段階的でよい）：あとで見る、SDK、閲覧数、高度な分析、経済的インセンティブ（後から追加可）

**Discord との役割分担**

- Discord：**会話・熱・所属** — Forge の代替ではない
- Forge：**版ごとの問い・育成の記録・変化を見る体験** — 完成前ゲームの育成に参加する公式の場

**フォローと初声（別概念）** — 2026-06 原典更新

| | フォロー（機能名） | 初声 |
|---|------|------|
| **意味** | 開発者への好意・期待（概念としての **「応援」**） | 開発者の問い、またはデフォルト問いへの返答 |
| **対象** | **開発者**（作品単位ではない） | 作品・版に紐づく声 |
| **性質** | 感情 | 情報（改善判断の材料） |
| **UI** | ボタン **フォロー** / サイドバー **フォロー中の開発者** | **フィードバックする** 等（概念上は声を届ける） |
| **統合** | **しない** — 初声しても自動フォローしない。フォローしても初声扱いにしない |

**作品単位の「応援」**

作品単位の応援は**主導線外のレガシー機能**として扱う。ゲスト対象にも、通常アカウント向けの新規拡張対象にも含めない。

- **主導線から外す** — 作品単位の「応援する」「応援中」ボタン・一覧は使わない
- 感情的な関心は **開発者フォロー** および継続的な関わり（プレイ・フィードバック・更新追跡）で扱う
- レガシーの support 系 DB/API（`project_supports` 等）が残っていても、UI に出さず、実装削除は別タスク
- 通常アカウントに登録したからといって作品単位応援が使える機能ではない
- 不満・批判・改善要望を伝えたい場合でも、開発者の問い・デフォルト問いには十分回答し得る。**感情と情報は分離**する

### 用語体系（概念層と UI 層）

Forge には **概念層**（原典・学習ループの整理）と **UI 層**（画面・Studio の呼び名）がある。全面統一を急がない。

| 概念層 | UI 層（例） | 関係 |
|--------|------------|------|
| 声を届ける | フィードバックする | UI は入口の総称。ユーザー向けに無理に「声を届ける」へ全面置換しない |
| **初声完了** | 回答を送信しました / 初声 N版（関わり表示） | 開発者の問い、またはデフォルト問いへの返答完了を内部・概念上 **初声** と呼ぶ |
| 詳しい感想（任意） | 詳しい感想を書く / FB N件 | 初声後の第2層。書かなくても初声完了は成立 |
| みんなの声（概念） | みんなのフィードバック（タブ名等） | 同じ公開面の別表現。名前を原典で固定しすぎない |
| 更新を追う | 更新を追う / 更新を追跡中 | 行動名 |
| 見届け人 | 見届け人 N（人数・バッジ） | 称号・結果。行動名ではない |
| あとで見る | あとで見る / **あとで遊ぶ**（詳細）/ **保存作品**（マイページ） | 概念名は **あとで見る**。画面ごとの揺れは当面許容 |

**フィードバック（UI 総称）の位置づけ**

- **許容する** — ボタン・タブ・Studio・ガイド等の日常 UI
- **意味** — 開発者に届く反応・改善材料の総称。**レビュー・採点・公開コメント欄ではない**
- **公開** — 個別回答の一覧化ではなく、**集計・傾向・改善材料**として扱う（§5）

### あとで見る（保存）

- **概念名**: あとで見る（ブックマーク）。学習ループのコアではない**別軸**
- 作品詳細 CTA では **あとで遊ぶ** も可（プレイ前のストック意図）
- マイページ一覧では **保存作品** も可
- 機械的な文言統一は急がない。いずれも同一機能を指す

### ブランドメッセージ

> **まだ誰も知らないゲームを、一緒に面白くする。**  
> 見つけて、遊び、反応を届け、成長を見届けましょう。

### トーン＆ビジュアル

- ダーク基調 × オレンジアクセント
- Steam × Product Hunt × インディーショーケース
- モダン・ポリッシュ・ややワクワク（子供っぽくしない）
- 管理画面っぽい平坦さは避ける

## 2. 判断基準

### 機能を追加・変更するとき

1. **学習ループ（初声→次版）を強化するか？** — 増幅のみの強化は後回し可
2. **原典の意味を変えていないか？** — 変えるならオーナー確認
3. **正式リリース初期版のスコープか？** — `docs/out-of-scope.md` を参照
4. **実装都合で仕様を歪めていないか？** — 技術都合より UX 原典優先
5. **単なる送客になっていないか？** — プレイ・反応・追跡が Forge に残るか

### 正式リリース初期版で含めるもの（2026-06）

- **フォロー** — 開発者単位。概念上の「応援」を UI 上はフォローで表現
- **共感** — 自由記述 FB のみ。投稿数に加算しない。声の重み・集約に反映
- **開発者 FB 評価** — 「開発に役立った」（開発者本人のみ非公開）
- **影響度スコア** — 信頼される見届け人の可視化。投稿数だけで強く評価しない
- **月間影響度ランキング** — 毎月リセット。過去入賞は実績・バッジに残す
- **実績・バッジ** — 活動サマリーではなく、獲得条件・進行状況の画面

### 依然として作らないもの（明示）

- 投げ銭・課金・販売
- 採用率のゲーミフィケーション（「提案採用 ○%」など）
- Forge SDK の**実装**（説明 UI のみ可）
- 新しい収益化機能
- **有料**ランキング・バッジ課金

**注**: 上記「含める」と「作らない」は矛盾しない — **コミュニティ機能のランキング・実績は可**、**金銭課金は不可**。

### 用語方針（ユーザー向け）

| 避ける / 内部 | ユーザー向け |
|---------------|-------------|
| テスター募集中 | **テストプレイ受付中** |
| テスター応募 | **テストプレイに参加** |
| 応援する（作品単位・連打で数字増） | **フォロー**（開発者・1人1回。投げ銭ではない） |
| 評価する、レビューする、星付け、採点 | **フィードバックする**（改善材料。レビューサイトではない） |
| 見届ける（操作名） | **更新を追う** |

**フィードバック** は UI 上の総称として広く使ってよい。原典・学習ループの整理では **声を届ける / 初声** を併記する。

## 3. ログイン・ゲスト・プレイヤー方針

### 基本思想

**「ゲームを見つける」は開放。** プレイヤーとして Forge に残す行動（保存・追跡・履歴・Studio 等）は **通常ログイン（Supabase Auth）必須**。  
ゲストは **Supabase Auth を使わない** — anonymous `user_id` は作らない。

**Forge に入るとき** — 「ログインする」または「ゲストで続ける」を選ばせる（入口ゲート）。  
作品詳細 URL 直アクセスでも、**未選択**なら入口ゲートを出す（クライアントオーバーレイ。OGP 配慮のため middleware 全リダイレクトはしない）。

**アカウントの種類**

| 種類 | 識別 | 用途 |
|------|------|------|
| **未選択** | entry mode 未設定・未ログイン | 一時状態。恒久ペルソナ「未ログインユーザー」は作らない |
| **ゲスト** | `localStorage` / cookie 等の **entry mode = guest** | 閲覧・外部プレイ・ゲスト FB（Phase 1）。**Supabase user_id なし** |
| **通常ログイン** | Supabase Auth（メール等） | フォロー、マイページ、通知、保存、追跡、履歴、Studio |
| **開発者** | 通常ログイン + 開発者プロフィール | 投稿・Studio・devlog |

**Supabase Anonymous Auth — 使わない（2026-07 確定）**

- Forge のゲストは **Supabase Anonymous Auth の匿名ユーザーではない**
- **`signInAnonymously` は通常導線から呼ばない**
- Dashboard の **Allow anonymous sign-ins は OFF** を維持
- migration **038 / 039**（`auth_is_registered_user()`）は **安全ガードとして残してよい**（ロールバック不要）

### 閲覧（セッション不要 — ゲスト選択後も可）

- トップ（ホーム）を見る
- ゲーム一覧・発見を見る
- ゲーム詳細を見る（開発ログ・公開集計の閲覧を含む）

### ゲストでできること（entry mode = guest）

- 上記閲覧
- **外部プレイリンクを開く** — `project_plays` / `project_play_sessions` に **保存しない**。プレイ人数にも **カウントしない**
- **フィードバックを送る**（Phase 1）— 表示名 **「ゲスト」**、`user_id` なしで作品側に保存。開発者が読める。**通常ログイン後に引き継がない**

### ゲストでできないこと — 通常ログイン必須

- Studio / 投稿 / マイページ / 通知
- あとで見る / 更新を追う / 見届け人 / バッジ / プレイ履歴
- 開発者フォロー
- ゲスト履歴の **通常ログインへの引き継ぎ**（意図的にしない）

### 通常ログインユーザー

- Supabase Auth の通常ユーザー
- Studio / 投稿 / マイページ / 通知 / あとで見る / 更新を追う / 見届け人 / バッジ / プレイ履歴が使える
- プレイは `project_plays` / `project_play_sessions` に記録する

### ゲスト — 技術・データ（2026-07 確定）

| 項目 | 方針 |
|------|------|
| 識別 | entry mode（`localStorage` 等）。Supabase `user_id` **なし** |
| プレイ | 外部リンクのみ。**DB 非記録**。人数集計に **含めない** |
| フィードバック | Phase 1: **ゲスト名義・user_id なし**で作品側保存（別テーブル/API 設計。未実装） |
| 引き継ぎ | 通常ログイン時に **引き継がない** |
| RLS 038/039 | 残す（万一 Anonymous が有効化されても write 遮断） |

**段階的拡張（原典上の目安）**

| Phase | 内容 |
|-------|------|
| Phase 0（現行） | entry mode、入口ゲート、ゲスト外部プレイ（DB 非記録）、登録導線 |
| Phase 1 | ゲスト FB のみ DB 保存（「ゲスト」名義・user_id なし） |
| Phase 2 候補 | あとで見る、更新を追う（**通常ログイン**のまま。ゲスト拡張は別途 GO） |
| Phase 2 以降 | 通知、マイページ等 — 通常ログイン必須のまま |

**UX・制約**

- ボタンは**非表示にしない**（現行どおり）
- ゲスト: **ゲストで続ける** → Auth を呼ばず entry mode 保存 → return 先または `/home`
- 登録ユーザー向け: `ログインしてプレイ` / `ログインしてフォロー` 等 → **`/login` へ**（モーダルで阻まない）
- **ゲストのプレイヤー行動を localStorage のみに永続化しない**（entry mode フラグのみ。§4）
- 本登録を促すタイミング: フォロー、マイページ、通知、保存、追跡、複数端末同期など

### 未選択・ゲスト・登録の UX（現行）

- **未選択** — 主要 Player 面で入口ゲート（ログイン / ゲストで続ける）
- **ゲスト** — 閲覧・外部プレイ可。保存・追跡・Studio 等は登録導線
- **登録済み** — ヘッダーにアカウント表示。ログアウトで entry mode もクリア
- ログイン成功後は return URL があれば復帰（ホワイトリスト検証）

### フォローの仕様

- 投げ銭**ではない** — 開発者への感情的応援（概念上の「応援」）を **フォロー** 機能で表現
- **対象は開発者** — 作品単位の応援ボタン・「応援中」一覧は使わない（§1 作品単位の「応援」）
- **1ユーザー1開発者あたり1回** — フォロー後は「フォロー中」表示
- サイドバー: **フォロー中の開発者**
- 連打で数字が増え続ける仕様は **NG**
- **ゲストでは不可** — 通常アカウント登録後

## 4. localStorage 方針

### 原則

**本番でユーザー間・端末間で共有されるべき情報は Supabase に保存する。**

localStorage は **下書き・UI状態・デモ用の一時データ** に限定する。

### Supabase に置くべきもの（例）

- ユーザー投稿プロジェクト（`projects`）
- 開発者プロフィール
- フォロー・ブックマーク（あとで見る）・更新追跡（更新を追う）・プレイ履歴 — **通常ログインユーザーのみ**
- フィードバック（初声・詳しい感想）— 登録ユーザーは `user_id` 付き。ゲスト FB は Phase 1 で **user_id なし・「ゲスト」名義**（別設計）

### localStorage でよいもの（例）

- **entry mode = guest**（Forge 入口選択。Supabase 非連携）
- フォーム下書き（未実装なら将来用）
- UI の折りたたみ状態
- **デモ・MVP 暫定**：通知、開発ログ、フォロー数、テスター応募数など（移行予定）
- 想定プレイ時間・開発者観点メモ等の **extras**（`forge-game-extras`）— 将来的に Supabase へ移行検討

### 禁止

- 登録ユーザー向けプレイヤー行動の結果を localStorage のみに保存する
- ゲストプレイを `project_plays` / `project_play_sessions` に保存する（人数集計に含めない）
- 「とりあえず localStorage」で本番共有データを永続化する
- Supabase Anonymous Auth でゲスト `user_id` を作る

## 5. フィードバック思想

### 位置づけ

**フィードバック**（UI 総称）は**レビューではなく、開発者に返る改善材料**。

- **レビュー・採点・公開コメント欄ではない**
- 開発者に届く改善材料として扱う。プレイヤー向け公開面は **集計＋個別テキストカード**（下記「みんなのフィードバック（公開面）」）
- 概念層では **声を届ける** と呼ぶ。UI で無理に全面化しない

「声を届ける」は **5 項目フォームを全部書くこと** ではない。  
プレイヤーサイクル上の **声を届ける / フィードバック** は **2 層**で構成する。

### 声を届ける / フィードバック（2 層）

**初回フィードバック（定義）**

初回フィードバックとは、**長文の詳細感想ではなく、その版に対する最小限の反応**である。開発者の問い、またはデフォルト問いへの回答を含む。この完了状態を内部的には **初声** と呼ぶ。

- **Phase 1（ゲスト）** — ゲスト名義・user_id なしの FB のみ（プレイ DB 記録なし）。詳しい感想は含まない
- **Phase 1（登録ユーザー）** — 上記の最小限の反応まで（初声）。詳しい感想は第2層
- 開発者に届く改善材料。**選択式の内訳そのものは公開しない** — 公開面は集計（上段）と、テキストとして残したい回答のみ個別カード（下段。下記）
- 長文の詳しい感想・深い FB は **任意の第2層**。Phase 1 の必須対象ではない

**1 段目：初声（初回フィードバック）**

- この **プレイ可能版** について、開発者が設定した **問い**（またはデフォルト問い）のうち、プレイヤーが **1 件以上** 返答を残した状態を **初声完了** とみなす（内部・概念上の呼び名）
- UI では **フィードバックする** / **質問に答える** / **回答する** 等。ユーザーに「初声」と強制表示しない
- プレイヤーは **0 問・1 問・複数問・全問** すべて自由。回答数の多少は評価しない。強制しない。
- 回答形式の例：選択式、はい/いいえ、3 択、1 行テキスト。
- **完了 = 初声完了**（問いへの返答が 1 件以上）。プレイヤー成功体験は **返事を届けた** で完結する。詳しい感想は不要。

**版プレイヤー問い（version_prompt）**

- 開発者は各 **プレイ可能版** に対して、プレイヤーへの問いを **複数** 設定できる（**上限 10 問**）。
- 同一版で複数仮説（チュートリアル、難易度、バランス、UI 等）を検証するのは自然な使い方。
- 旧来の「特に見てほしい観点」（focusNotes）の思想を、**版に紐づく問い** として再定義する。
- 問いが多いほど回答率が下がる可能性がある — 開発者 UI に **注意喚起** を表示する。

**デフォルト問い（開発者が問いを設定しない場合）**

- 開発者が問いを 1 件も設定していない版では、プラットフォーム **デフォルト問い** を提示する。
- デフォルト例：**もう一度遊びたい？**（`would_replay` と整合：もう一度遊びたい / 更新次第また遊びたい / 今はもう遊ばない）
- デフォルト問いも、プレイヤーへの **返答任意**（0 問回答可）。

**2 段目：詳しい感想（任意）**

- 熱量が高いプレイヤー向けの **任意追加**。成功体験には含めない。**ゲスト Phase 1 の対象外**
- 項目（構造化）：
  - 良かった点
  - 気になった点
  - バグっぽい挙動
  - 自由記述
- 初声完了とは独立。書かなくても **フィードバック完了（初声）** として扱う。

**みんなのフィードバック（プレイヤー向け公開面）**

- **概念名**: みんなの声（原典・設計整理用）
- **UI 名の例**: みんなのフィードバック（タブ名等）— 固定の正式名称ではなく、伝わる表現として許容
- **上段 — 集計**: 選択式・再プレイ意向等の **件数・比率・グラフ**。個別の選択内容・共感・通報は付けない
- **下段 — 個別テキストカード**（2 種類のみ）:
  - **A — 問いへの補足 / 短文**: 選択式問いへの **任意コメント**、または `short_text` 問いへの回答本文。**選択肢そのものは出さない**
  - **B — 詳しい感想**: **1 投稿 = 1 カード**。表示フィールドは **良かった点 / 気になった点 / バグっぽい挙動 / その他** の 4 項目のみ（`focus_response` / `would_replay` は公開 UI に出さない）
- **著者表示**: 登録ユーザーは **表示名＋アバター**（任意）。ゲストは **「ゲスト」** バッジ。**メール・email プレフィックス・user_id・submitter_key・内部 UUID は公開しない**
- **読み取り**: 公開カードは **専用 RPC** 経由のみ（テーブル直接 SELECT 不可）。カード識別子は **opaque な `card_id`**（内部 UUID をそのまま露出しない）
- **共感**: **テキストカードのみ**（選択式集計には付けない）。実装はカード公開の後段
- **通報**: **テキストカードのみ**（登録ユーザーのみ、初期）。`POST /api/feedback/report` 経由。**自動非公開はしない**（記録 → Studio / 運営確認）
- **モデレーション**: 公開後の **非表示**（削除ではなく `hidden`）。理由必須（オーナー操作）
- **送信前同意**: チェック必須。「投稿したフィードバックは、作品ページの『みんなのフィードバック』に表示されます。個人情報や公開したくない内容は書かないでください。」（同意時刻等の DB 監査列は持たない）
- **既存 FB**: 同意列なしで **すべて公開対象**（`legacy_private` 等は設けない）
- デモ作品はサンプル表示可。実データ優先

**公開される反応の集計（開発者向け）**

- 開発者は **次に何を直すか** が伝わる状態を目指す。
- 単なるアンケート集計（例：武器A 41% / 武器B 59% の並列だけ）は **不十分**。
- 望ましい流れ：**数字 → 解釈 → 改善の示唆**。
- 例：「武器Bを好むプレイヤーがやや多いが、A派も4割存在」「チュートリアルは概ね伝わっているが、約3割は分かりづらさを感じている」
- AI 集約は **開発者支援** として導入可。プレイヤー代替・自動返信は NG（§7）。

### 導線（順序が重要）

```
ゲームを理解する
  ↓
プレイする
  ↓
初回フィードバック（初声＝開発者の問い、またはデフォルト問いへの返答）
  ↓
（任意）詳しい感想
```

詳細ページを開いた直後に「評価して」「コメントして」「レビューして」と**迫らない**。  
プレイ直後は **問いへの短い返答** を優先し、詳しい感想は **折りたたみ・任意** とする。

### ユーザー向け copy の方針

| 避ける | 使う（例） |
|--------|------------|
| 評価する、レビューする、星付け、採点、アンケート | フィードバックする、質問に答える、この版について教えてください |
| 改善材料を全部書いて | 詳しい感想を書く（任意） |

**フィードバック** を UI 総称として使ってよい。上記「避ける」は**ニュアンス**の話であり、単語「フィードバック」自体は禁止しない。

### 開発者側

- 開発者が**何を採用するかは開発者が決める**
- **問いの中身は開発者が決める** — Forge はゲーム開発の専門家ではない。問いの設定・集計・改善接続を支援する（事業仮説 §7）
- 開発者が **参考になった** 声を評価できる（非公開）。Good レビュアー判定の主体は開発者
- 「ユーザー意見に従え」と見える表現は避ける
- プレイヤー提案採用は**実績として見せてよい**が、義務化しない
- **1 版・最大 10 問** — 問いは版公開の意図とセットで設定する。多すぎる問いは回答率低下の注意喚起を表示
- **回答率・回答数をプレイヤーに評価として見せない**

## 6. マネタイズ仮説

> **現時点は仮説。MVP では収益機能を実装しない。**

### 前提

- プレイヤー体験は **無料** が原典に沿う
- **学習ループが回ること**が最初の価値。課金は無料期間後（事業仮説: `docs/forge-business-hypothesis.md`）

### 将来あり得る方向（未確定・未実装）

1. **開発者向けツール** — 詳細アナリティクス、更新告知、テスター管理の高度化
2. **Forge SDK（任意）** — 匿名プレイデータ（プレイ時間・到達率等）。導入しなくても Forge は使える
3. **露出・プロモーション** — 完成前作品の featured 枠等。**おすすめ順をフォロワー数だけで支配しない**（月間影響度ランキングは別画面）
4. **コミュニティ・支援** — 投げ銭ではなく、**フォロー**（開発者への応援）の延長

### やらないこと（収益化）

- 投げ銭、課金壁、作品販売
- ランキング課金、バッジ課金
- プレイヤーに金銭を払わせる体験

## 7. AI機能方針

### プロダクト内（Forge アプリ）

| 項目 | 方針 |
|------|------|
| AI サムネ生成 | **Coming Soon 表示のみ** — 外部 API は MVP で使わない |
| AI フィードバック要約 | 未実装 — **開発者向け**公開集計の **解釈・改善示唆** 生成に利用可。プレイヤー向けに個別テキストを AI 生成で差し替えない（§5） |
| AI による自動返信 | **NG** — 人間のプレイヤーの声を尊重 |
| Forge SDK | AI ではない — 匿名プレイデータ取得の任意機能（将来） |

**AI 集約の位置づけ（開発者向け）**

- 目的：**次に何を直すか** が伝わること。ダッシュボード型の数字並列だけにしない。
- 入力：問い別の集計（件数・比率）。詳細 FB・Studio 向け個別行は開発者画面で参照可。
- 出力：解釈文・改善示唆（例示は §5「公開される反応の集計（開発者向け）」）。
- プレイヤー向け UI では AI 生成文をそのまま出さず、**集計グラフ＋プレイヤーが投稿したテキストカード** を主とする。

### 開発プロセス（ChatGPT × Cursor）

**ドキュメントの役割**

| ファイル | 用途 | 更新タイミング |

## 8. その他の判断軸

### 発見（Discovery）

- 「次にハマるゲームを**完成前に**見つける」体験を最優先
- Steam ほど複雑なフィルタにしない
- 軸の例：ジャンル、開発フェーズ、想定プレイ時間、テストプレイ受付、プレイ環境

### 詳細ページ

- 「なぜ**今**このゲームを遊ぶべきか」が伝わる情報を上部に
- タブ例：概要 / 開発ログ / 公開される反応の集計（UI では「みんなのフィードバック」等）
- 開発ログ / 履歴で「育っている感」を出す（v0.1, v0.2…）
- 外部リンク・プレイ URL は明示。安全に関する注意書きを添える

### 変化を見る（プレイヤー）

- プレイヤーは devlog・新版公開・（将来）参考にした声を通じて、**ゲームの育ち**と**自分の返答が育ちに繋がったこと**を確認できる
- **変化を見る** はプレイヤーサイクルの**増幅**。初声で学習ループは始まる。変化を見せると価値が上がる
- リアルタイム返信やチャット機能は必須ではない — **記録として残る成長** が Forge の強み

### データ・インフラ

- 認証・永続データ：**Supabase**
- デプロイ：**Vercel**（想定）
- 日本語 UI。サービス名 **Forge** は英語表記のまま

### ドキュメント更新義務

**毎回（通常タスク完了時）**

1. `docs/forge-changelog.md` — ユーザー体験・仕様の変化

**節目・大きな仕様変更・本番反映時**

2. `docs/forge-handoff.md` — 現在地の更新（通常タスクでは必須ではない。`AGENTS.md` 参照）
3. `docs/chatgpt-handoff.md` — 新スレッド引継ぎが必要なときのみ

**原典・仕様判断の変更時**

- `docs/forge-principles.md` 自体の更新はオーナー GO のうえ changelog に記録する
- 原典 v2 のような大きな意味変更は handoff にも残す
