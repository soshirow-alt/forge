## 1. 現状の構造（P1-2 deploy 時点）

```
[ヘッダー] 開発ダッシュボード          [作品を投稿する] ← 常に primary 強調
[次にやること] ← 複数カード（FB件数 / 最新FB / pending / no-devlog）
[フィードバック inbox] ← 全作品横断、各カードに devlog + 詳細 CTA
[作品管理テーブル] ← 4ボタン/行 + FBバッジ
[アナリティクス / SDK]
```

**オーナー指摘との対応**

| 指摘 | コード上の原因 |
|---|---|
| 重複感 | `feedback_summary` + `latest_feedback` が連続表示（`buildDeveloperNextActions` L86-112） |
| CTA 散在 | Panel 2ボタン × N カード + inbox 2ボタン × M 件 + テーブル 4ボタン |
| FB 主役 | ページ上半分が FB 横断 inbox 構造。作品メタ（版・更新日）が弱い |
| 投稿 CTA 過強 | `my-projects-page` L148-154 が常に gradient primary |

## 2. P1-2.5 設計原則

1. **主役は作品の成長** — FB は「材料」、画面の主語は作品タイトル
2. **開発者の仕事は2つだけ** — ① 声を確認する ② 次の版を作る（devlog）
3. **Primary CTA は1画面1つ** — 作品ごとに「開発ログを書く」または「新版として公開する」
4. **Inbox ではなく Studio 寄り** — 横断 FB 一覧は補助。作品単位のブロックが本体
5. **投稿 CTA は文脈依存** — 改善フェーズでは tertiary / ヘッダー右端を弱める

Forge 原典位置づけ:

```
プレイヤー: FBを書く
開発者:     次の版を作る（devlog → 版公開）
```

## 4. セクション定義

| セクション | 役割 | FB の扱い |
|---|---|---|
| **作品ヒーロー** | 今フォーカスする1作品の成長サマリ + Primary CTA | FB件数はバッジ1行のみ。本文は出さない |
| **プレイヤーの声** | 最新FB 1件表示 + 過去は折りたたみ | 読む場所。CTA は置かない（ヒーローに集約） |
| **開発の進捗** | 版・devlog数・最終更新 | 版公開への secondary 導線 |
| **すべての作品** | 複数作品時の切替 | FB件数バッジのみ |

**廃止・統合**

- ~~NextActionsPanel 複数カード~~ → **作品ヒーロー1枚**に統合
- ~~横断 FB inbox（全件フル表示）~~ → **作品別「プレイヤーの声」**に内包
- ~~作品管理テーブル（4ボタン行）~~ → **コンパクトカード**（2リンクまで）

## 5. CTA 階層（整理後）

| 優先度 | ラベル | 条件 | 遷移先 |
|---|---|---|---|
| **Primary** | 開発ログを書く | 作品あり（デフォルト） | `/projects/{id}/devlog/new` |
| **Primary  alt** | 新版として公開する | devlog あり & FB 対応済み後 | 同上（copy 違いのみ） |
| Secondary | 作品詳細 | 常時 | `/games/{id}` |
| Tertiary | 投稿を編集 | 常時 | `/projects/{id}/edit` |
| Tertiary | 作品を投稿する | 作品0件のみ Primary | `/submit` |
| Hidden default | フィードバックを見る | アンカー不要 — 同一画面内スクロール | `#player-voice` |

**削除する CTA 文言**

- 「フィードバックを見る」（独立ボタン）
- 「最新FBから開発ログを書く」
- 「このFBをもとに開発ログを書く」（inbox 内 — ヒーローに統合）

## 6. 重複排除ロジック

| Before（P1-2） | After（P1-2.5） |
|---|---|
| feedback_summary カード | 作品ヒーローの「新しいFB N件」1行 |
| latest_feedback カード | プレイヤーの声セクション最新1件 |
| inbox 全件フル + 各 devlog CTA | 最新1件展開 + 過去折りたたみ、CTA なし |
| pending / no-devlog 複数カード | ヒーロー Primary ラベル切替のみ |

**フォーカス作品の選び方（B2 ヒューリスティック流用）**

1. FB あり & devlog 未対応 → その作品
2. 複数該当 → 最新 FB の作品
3. FB なし → 最新更新 or 最初の作品
4. 0 件 → 投稿誘導

## 7. 「作品を投稿する」CTA の扱い

| 状態 | ヘッダー右上 |
|---|---|
| 作品 0 件 | **Primary**（gradient）— 現状維持 |
| 作品あり & FB 0 | Secondary（outline） |
| 作品あり & FB あり（改善フェーズ） | **Tertiary**（テキストリンク or 小ボタン） |

改善フェーズで強調すべきは **開発ログを書く** のみ。

## 8. 案 C（作品別 Studio）との境界

| P1-2.5 In | 案 C Out |
|---|---|
| 1 作品フォーカスのヒーロー | 作品ごと独立 URL `/studio/{id}` |
| 既存 `/my-projects` 内 IA 変更 | 版タイムライン UI 新設 |
| devlog / 版公開 deep link 維持 | 分析ダッシュボード |
| 折りたたみ FB | FB 通知 Supabase 化 |

**案 C 再開条件（従来どおり）**

- 複数作品 3+ でフォーカス切替が煩雑
- P1-2.5 後も「作品の成長」が伝わらない
- 版履歴・stats の一覧性が不足

## 10. レビュー観点（GO 前チェックリスト）

- [ ] 作品タイトルが画面で最初に目に入るか
- [ ] Primary CTA が1つに絞れているか

## 11. オーナー判断ポイント

1. **レイアウト**: 3-A（1作品ヒーロー型）で GO するか
2. **複数作品**: フォーカス1 + コンパクトリストで足りるか
3. **FB 折りたたみ**: 過去 FB はデフォルト閉でよいか
4. **Primary ラベル**: 常に「開発ログを書く」か、状態で「新版として公開する」に切替か
5. **テーブル**: 完全廃止 vs コンパクトカード化
