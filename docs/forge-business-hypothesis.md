## §0 一言定義（現在地）

**Forge は、完成前のゲームとプレイヤーを繋ぎ、版ごとの学習ループを回し、その過程で価値あるレビュアーが可視化されていく場所。**

- テスター募集サイトではない
- 発掘だけのサイトでもない
- 有償テスター代替が本体価値ではない

Steam は「完成したら来てね」。Forge は「完成してなくていいよ」。

## §1 問いの変遷

| 時期 | 問い |
|------|------|
| 当初 | どうやってマネタイズするか |
| 現在 | Forge は何を売るサービスか |
| 直近の正しい問い | **どうやって普通のプレイヤーから Good レビューを引き出すか** |

スーパーレビュアーをいかに作るか — これは**誤った問い**（将来検討）。  
まずは **Good レビュー** を増やす。

---

## §2 無料期間の定義

無料期間は「売上を諦める期間」ではない。

**レビュー供給の因果を証明する期間**（リリース後 半年〜1年 完全無料を想定）。

証明したいこと:

1. ゲーム供給が集まる
2. プレイヤー供給が集まる
3. 初声（版に紐づく声）が発生する
4. 初声が開発者の意思決定に使われる
5. Good レビュアーの芽が生まれる

価値を感じなければ解約でよい（課金導入後）。現時点は**供給形成が優先**。

---

## §3 ターゲット（A / B / C）

| 層 | 定義 | 初期優先 |
|----|------|----------|
| **A** | テスト価値を理解。Discord だけでは不足。有償テスター利用経験あり。テスト予算あり | **最優先** |
| **B** | テスト価値は理解。Discord/X 利用。レビュー品質に不満 | 二次 |
| **C** | テスト文化が薄い。モチベーション低い | **狙わない** |

C 層を大量に集めると初声の質が落ち、学習ループが回ったように見えて回っていない状態になる。

---

## §4 本命価値 — 学習ループ

```
版 → プレイ → 初声 → 次に直すこと → 改善 → 次版
```

開発者が欲しいのは「レビュー」ではなく **意思決定材料**:

- 面白いか
- どこで離脱するか
- 何が刺さるか / 刺さらないか
- 次に何を直すべきか

**プロダクト言語の正**: 版ごとの学習ループ  
**結果の説明**: 売れる確率を上げる情報

### 有償テスター代替の位置づけ

- **本体価値ではない**
- A 層向けの**販売文句・比較対象**としては有効（テスト予算の一部）
- 奪う予算は広告費ではなく**テスト運用コスト**

---

## §5 プレイヤー価値

### 確定

- プレイヤーは開発者を助けに来ない
- **入口価値は発掘** — 面白そうな未完成ゲームを見つける
- 結果として開発者が助かる

### プレイヤー層モデル

| 層 | 行動 | 事業上の意味 |
|----|------|-------------|
| L0 | 発掘 → プレイのみ | 入口検証 |
| L1 | 初声 | **North Star の核心** |
| L2 | 継続レビュー | 供給の厚み |
| L3 | 高品質・再依頼 | Good / スーパーレビュアー候補 |

### 継続動機（未確定・層別）

承認・実績・経済・貢献・ゲーム愛・開発者愛 — 単一の本命は置かない。  
**発掘＝流入、承認＋影響力可視化＝継続の候補**（経済は後からの増幅）。

### Forge と Discord

- 既存ファン → Discord
- 新規発掘 → Forge
- 代替ではなく**補完**

---

## §6 レビュアー / Good レビュアー / スーパーレビュアー

**混同禁止。別概念。**

| 用語 | 定義 |
|------|------|
| **レビュアー** | 面白かった・つまらなかった等の反応を **1 回** 返す人 |
| **Good レビュアー** | 開発者にとって**有益な**フィードバックを **1 回** 返す人 |
| **スーパーレビュアー** | Good レビューを**継続的・複数回・複数作品**で返す人 |

- **現在の主論点**: Good レビューをいかに引き出すか
- **スーパーレビュアー**: 将来検討。MVP・無料期の柱にしない
- **品質判定者は Forge ではない** — **開発者**（非公開「参考になった」等）

### 良レビュアー / スーパーレビュアーの順序（中長期）

1. 学習ループが回る
2. 開発者が「また欲しい声」を評価する
3. 評価履歴が貯まる
4. Good レビュアー・スーパーレビュアーグラフができる
5. 将来的に副業化・案件が見える（未確定）

## §7 Good レビュー生成 — 最低条件（施策ではない）

Forge が成立するための**土台**。Good レビュー生成環境は、構造化初声・学習ループ・良レビュアー可視化の**3 層すべての基盤**。

### 1. 導線

プレイ後に**自然に**声を出せる。詳細を開いた直後に評価を迫らない（原典 §5 と整合）。

### 2. 回答しやすさ

自由記述だけにしない。**開発者が版ごとに問いを設定**できる（Forge はゲーム開発の専門家ではない — 問いの中身は開発者が決める）。

Forge の役割:

- 問いを**設定しやすくする**
- 回答しやすくする
- 集計しやすくする
- 改善に繋げやすくする

将来あり得る: 同ジャンルでよく使われる問いの推薦 — **後回し**。

### 3. 承認

開発者が参考になった声を**評価**できる（非公開）。

### 4. 影響力可視化

プレイヤーが以下を認識できる:

- 読まれた
- 採用された
- 改善に繋がった

### 経済インセンティブ

上記 4 つとは**別レイヤー**。最低条件ではない。後から追加可能な**増幅装置**。

現方針: **承認・影響力可視化だけで**どこまで Good レビューが出るかを見る。金銭要素は必要になったら追加。文化を変えるリスクがあるため初期導入は慎重。

## §8 見届け人

**必須条件ではない**（棄却済み仮説から撤回）。

- **価値増幅装置** — いれば Forge の価値は大きく上がる
- いなくても学習ループ単体で開発者価値は成立しうる
- 詳細: `docs/witness-tier-design-review.md`、原典 §1

---

## §9 Forge の価値 — 3 層構造

| 層 | 内容 |
|----|------|
| 1 | **構造化された初声**（版・問い・集計） |
| 2 | **学習ループ**（次に直すこと → 改善 → 次版） |
| 3 | **良レビュアーの可視化**（開発者評価・影響の記録） |

Good レビュー生成環境（§7）はこの 3 層の土台。

## §10 最大資産

| 候補 | 評価 |
|------|------|
| A ゲームDB | プレイヤー獲得に必要。早期 moat は弱い |
| B レビュアーDB | 中長期の競争優位候補 |
| **C 学習ループデータ**（版→声→決定→次版） | **現時点最有力** |

重要なのはレビュー**数**ではなく、開発者が「この人のレビューまた欲しい」と思う**関係**が残ること。

## §12 North Star（事業）

### 一文

**プレイしたプレイヤーのうち、十分な割合が「版に紐づく初声」を残し、その声が開発者の優先順位決定に使われるか。**

### 分解指標 M1〜M4

| ID | 指標 | 定義 |
|----|------|------|
| **M1** | プレイ→初声率 | 当該版プレイ UU のうち初声完了 UU |
| **M2** | 初声→参考になった率 | 開発者が非公開評価した初声 / 初声総数 |
| **M3** | 初声→次に直すこと決定率 | Studio 上位課題採用 or 開発者が言語化 |
| **M4** | 決定→実改善率 | 次版・devlog で変更が追える |

**「十分な割合」**: 初期は A 層パイロット 3〜5 作品での相対比較から閾値を後置き（例: M1 ≥20% は仮・P0 計画参照）。

### Good レビューとの関係

North Star は **初声と意思決定** を測る。Good レビューは **M2 + 開発者インタビュー** で判定。スーパーレビュアー指標は無料期の主 KPI にしない。

## §13 未解決論点

- プレイヤー継続レビューの本命動機（層別の重み）
- イエスマン問題 — 開発者が気持ちいいレビューばかり評価するか（未検証）
- A 層の実 TAM
- 経済インセンティブ導入のタイミング
- 再プレイの事業上の位置づけ（増幅 vs 必須）— 現方針は**増幅**
